`docs/SHOPIFY_APP_REQUIREMENTS.md` §11.2 は「Shopify Admin GraphQL API 呼び出しは型を先に確認してから
構築する…フィールド名を推測で書かない」と明文化している。しかし本エージェントは shopify.dev への
ネットワークアクセスや実際のPartner Dashboardでのスキーマ確認ができない環境で実装する場合がある
(Shopify の「App Events API」のような、要件ドキュメントには存在自体は書かれているが具体的な
ミューテーション名・引数名までは書かれていない機能)。

この場合、実装を止めるのではなく、GraphQLクエリ文字列(またはリクエストボディ組み立て)を
**1つの定数/1つの関数に閉じ**、その直前に「現時点の理解に基づく暫定実装。実機確認は別途行うこと」
という趣旨のコメントを明示して進めた。テストは実際のShopify側の振る舞いではなく
「自分のコードが期待通りのリクエストを組み立てているか」だけを検証する(fetchをモックする)。

**Why:** タスクの完了条件(`pnpm verify` 通過、mock fetchでのテストカバレッジ)は実機確認を要求しておらず、
要件ドキュメント自身も D-2(実際の請求反映確認)を「§7 受け入れ条件」として実装後の別ステップに
分離している。ここで実装を止めると後続タスクが完全にブロックされるため、「確認済み」を偽装せず
正直に暫定である旨を残しつつ実装を進める方が、要件文書の精神(推測を隠さない)に合致する。

**How to apply:** 第三者APIの正確なワイヤーフォーマットが確認できないとき:
1. リクエスト組み立てを1つの定数(例 `APP_EVENTS_MUTATION`)または1つの純粋関数に集約する
2. その直前のコメントで「暫定実装・要実機確認」と明記し、確認後にどこを直せばよいか1箇所に絞る
3. テストは「自分のコードの入出力」だけを検証し、第三者の実際の応答形式を前提にしない
4. 確度の高い部分(HTTPメソッド・認証ヘッダ名・エンドポイントのURL構造)は、既存コード
   (このリポジトリでは `exchangeShopifyAccessToken` 等)で既に確認済みのパターンを再利用する
