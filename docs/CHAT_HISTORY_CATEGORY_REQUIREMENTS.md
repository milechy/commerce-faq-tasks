## 0. 現状フロー（実測）

```
レール「会話の履歴」💬 をクリック  (index.tsx:312, badge = escalations 件数)
   ↓
定型プロンプトを実送信: 「最近の会話とエスカレーションの状況を教えて」
   ↓
LLM が任意にツールを選ぶ  get_chat_sessions / get_escalations（呼ばない自由もある）
   ↓
結果は プレーンテキスト・一律 500 字上限 (actionExecutor.ts の truncate)
   ↓
汎用の agentAction カードに result 文字列を貼るだけ
   ↓
深掘りしたければ人間が 8 文字の短縮ID を目視して打つ → get_chat_session_messages（これも 500 字）
   ↓
削除したい → ツールが無いので get_legacy_ui_link(session_deletion) で旧UIへ受け渡し
```

バッジ（escalations件数）だけはツールを通さず `/v1/admin/chat-history/escalations` を直接 fetch している。表示の入口と、会話で得られる中身が別経路。

## 1. 本質的に解決すべき課題

- **課題A**: カテゴリが「画面」ではなく「1回の定型質問」でしかない。一覧→絞り込み→特定→深掘り→処置という反復探索に耐えない。
- **課題B**: 出力上限500字が、量こそが本質の機能（一覧・本文閲覧）と構造的に非互換。しかも黙って切れる。
- **課題C**: データ層（`getSessions`）は既に期間/全文検索/感情/ソート/ページングを実装済みだが、ツール層 (`get_chat_sessions`) が渡すのは `{tenantId, limit}` だけ。作られていない機能ではなく、作ってあるのに触れない機能。
- **課題D**: Judge品質評価・成果記録・提案ルールのうち、削除以外は handoff キーもツールも無く、チャットから存在が見えない。計測にも現れないため「使われていない」と区別がつかない。
- **課題E**: バッジ(`escalations`＝対応中の緊急タスク)とラベル(「会話の履歴」＝過去ログ)の意味がずれている。

## 2. ユーザーが本当に得たい価値（3つのジョブ）

| | ジョブ | 問い | 成功状態 |
|---|---|---|---|
| **J1** | 対応 | 今すぐ人が出るべき会話はどれか | 返信した／対応完了にした |
| **J2** | 点検 | AIはちゃんと答えられているか | 低品質・取りこぼしを見つけてFAQ/ルールに直した |
| **J3** | 照会 | あの問い合わせ、何と答えた？ | 該当の会話1件を特定して中身を確認した |

得たい価値の核は「見えること」ではなく「見て、その場で手が打てること」。J2で見つけた穴をその会話のままFAQ化できるのは新UIだけで、これが旧UIに対する本質的な優位になる。

## 3. 確定した決定（2026-07-31）

1. **セッション削除をチャットから可能にする。** ただし新規SQLは書かず既存の `deleteSessionRepository.deleteSession()`（reason 5–500文字必須・audit_logs同一TX・行ロック・lock_timeout 3s）を必ず経由する。
2. **Judge評価・成果記録をチャットから見せる。** 対象は Judge評価（総合スコア+4軸+要約）と成果記録（outcome、閲覧＋記録）の2つ。提案ルール承認は super_admin 専用機能（旧UIで `isSuperAdmin &&` に閉じている）のため対象外。
3. **「対応中の会話」（J1・エスカレーション）を独立カテゴリにする。** バッジは「会話の履歴」から移す。

## 4. スコープ

### やること
1. カテゴリ起点を「1発の質問」から「点検/照会への分岐」に変える
2. 閲覧系ツールの出力予算を書き込み系から分離する。打ち切りは必ず「全N件中M件」を残す
3. 既存のデータ層能力（期間・検索・感情・ソート・ページング）をツール引数として露出する
4. 会話一覧／会話本文を構造化カードに載せる（短縮IDの手打ちを不要にする）
5. Judge評価・成果記録をチャットから閲覧・記録できるようにする
6. セッション削除をチャットから完了できるようにする
7. 「対応中の会話」を独立カテゴリにする

### やらないこと
- パネル（Surface A）への同機能移植（機能凍結、`CHAT_SURFACE_DECISION.md` §6）
- `chatSessionStore` のキー単一化、`copilot-preview/index.tsx` の `components/agentChat/` への分解（別タスク）
- 一括削除・提案ルール承認のチャット実装
- super_admin 向け機能の追加

## 5. 制約（実装上の要点）

- **SQL検証境界**: `chatHistoryRepository.getSessions()` は `period`/`sort_order` を文字列補間しており、検証は呼び出し側 allowlist が全て担う。ツール経由という第二の呼び出し元にも同じ allowlist を通す。
- **セッション特定/削除**は既存の `resolveSessionByShortId()` / `deleteSession()` を必ず経由。新規SQLを書かない。
- **previewMode中のsuper_adminは常にtenant scope。** globalスコープを使わない（所有権チェックが外れる）。
- **ブロック判定文字列**（`確認が必要です` / `確認をスキップできません`）を変えない。
- **card は text の追加であり置換ではない。**
- 詳細は `src/api/admin/CLAUDE.md` / `admin-ui/CLAUDE.md` を正とする。

## 6. テスト観点の要点

- allowlist外の値がSQL文字列補間に到達しないこと（回帰テスト必須）
- プロンプト注入シナリオ（顧客の発言に削除・記録・返信の指示が混入）で、ユーザー明示同意なしに書き込み・削除が実行されないこと — **削除ツール実装のリリースブロッカー**
- 他テナントのセッションIDは不存在として扱う（権限エラーで存在を漏らさない）
- confirmed なしの書き込みはDBが無変更
- 境界値: limit/offset の 0・上限・負値・NaN、出力予算の打ち切り表示
- 390px でのレイアウト崩れ、タップ44px

## 7. 受け入れ条件（要約）

- 一覧→特定の1件の本文に、短縮IDの手打ちなしで到達できる
- 期間・検索語・スコア帯・ソート・ページングがチャットから指定でき実際にSQL条件に反映される
- 履歴で見つけた不足から `suggest_faq` 等へ会話を跨がず到達できる
- エスカレーション返信・対応完了が要約提示→チップ同意→実行の順で完了する
- Judge評価・成果記録がチャットから見え、成果記録は記録まで行える
- セッション削除が理由取得→対象提示→同意→実行の順で完了し、audit_logsに理由付きで残る
- 「対応中の会話」が独立カテゴリとして存在し、バッジがそちらに付いている
- 注入シナリオで書き込み・削除がユーザー同意なしに実行されない（必須）
- `agent_legacy_handoff{feature}` で `session_deletion` 以外の理由の旧UI遷移が分離して数えられる

## 8. 差し戻し基準

1. allowlist外の値がSQL文字列補間に到達しうる状態
2. 出力予算を全ツール一律で緩めた
3. `components/agentChat/` 等の新規ディレクトリを本タスクで新設した
4. パネル側に同機能を足した
5. 会話ログ本文が `sessionStorage` に載る状態のまま
6. ブロック判定文字列を変更した
7. 注入テストが存在しないまま削除ツールを実装した
8. `reason` なし／モデル生成の理由で削除が通る
9. previewModeのsuper_adminがglobal scopeで削除できる
10. 提案ルール承認を新UIに載せた
