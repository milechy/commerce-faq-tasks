## 0. 前提となる本番の実態

要件の優先順位・同意の設計・判定基準は、すべてこの数字の上に立っている。

|---|---:|

## 1. 本質的に解決すべき課題

> **R2C は「会話から学ぶ仕組み」を何重にも持っているのに、会話が一度もその仕組みに流れ込んでいない。**

問題は機能の不足ではなく、**機能同士をつなぐ矢印が切れている**こと。Judge・提案・承認・A/B・Hermes・メモリは各々「完成」しているが、入口（会話→評価）と出口（承認→本番プロンプト）が断線しているため、1,041 会話分の経験がゼロ件の学習に変換されている。

| 層 | 課題 | 監査での現れ方 |
|---|---|---|
| **① 売る振る舞い** | セールス会話の段階（聞く→提案→推す→締める）が進まず、常に「聞く」に留まる | SalesFlow が毎ターン clarify 固定。商品カード・心理学原則・反論対応・close が到達不能 |
| **② 経験を評価に変える** | どの会話が良かった/悪かったかが記録されない | Judge 本番不発火（4/1,041）。離脱セッションは設計上そもそも評価対象外 |
| **③ 評価を振る舞いに戻す** | 評価から生まれた提案が承認されても、本番の振る舞いが変わらない | 承認が `is_active` を立てない。Hermes 提案に適用先無し。variant 割当が消える。効果を測る JOIN が無い |

3層は直列依存。①が直らなければ②で評価すべき「セールス行動」が存在せず、②が直らなければ③に流す材料が無い。逆に③だけ直しても承認する提案がゼロのまま。

## 2. ユーザーが本当に得たい価値

| ステークホルダー | 表面的な要望 | 本当に欲しいもの |
|---|---|---|
| **テナント（店舗・EC 事業者）** | 「賢いチャットボット」 | **放っておいても月を追うごとに CV が上がる営業担当**。設定作業ではなく成果。自店の会話が自店の成績に還元されること |
| **R2C 運用（super_admin）** | 「Hermes で学習させたい」 | **知見が個々のテナントに自動で配られる**こと。ただし勝手に書き換わらず、何が変わったか・効いたかが見える状態で |
| **エンドユーザー（来訪者）** | — | 聞きたいことに答え、買うべきものを自然に勧め、嘘（「今なら」等）を言わない相手 |

**価値の定義:** 「テナントごとの会話が、人間の最終承認を経て、そのテナントの次の会話を改善する」が、運用者の手作業なしで毎日回っている状態。**他テナントへの展開はその次**（§0 前提 2）。承認 UI を増やすことではなく、**承認 1 回が確実に会話に反映され、その効果が数字で返ってくる**ことが価値。

CLAUDE.md の原則「価値が生まれる地点はエンドユーザーとの会話であって管理画面の設定作業ではない」と整合する。

## 3. スコープ

### やるべきこと

| ID | 要件 | 層 |
|---|---|---|
| **R1** | **セールス段階が会話の進行に応じて遷移する。** 前ターンの段階が次ターンに引き継がれ、propose / recommend / close に到達できる。段階ごとの既存実装（テンプレ・商品カード・心理学原則）が実際に使われる。**テナント単位で段階的に開放できる**（D6） | ① |
| **R2** | **本番会話が自動で評価される。** 明示終了だけでなく離脱・放置セッションも一定時間後に評価対象。評価コストはテナント単位で上限管理でき、費用が事前に明示される | ② |
| **R3** | **承認が本番に効く。** どの経路（テナント詳細 / copilot / 旧 tuning ページ）で承認しても次の会話から振る舞いが変わる。承認状態の表現が 1 つに統一される | ③ |
| **R4** | **変更の効果が測れる。** 各応答に「どのルール・どの variant が効いたか」が記録され、あり/なしで Judge スコアと CV 率を比較できる。結果が承認者に見える | ③ |
| **R5** | **A/B variant の割当がセッションに固定され、記録され、勝者を本番プロンプトへ昇格できる** | ③ |
| **R6** | **提案の受け皿（棚）を 1 つにする。** Judge 由来・Hermes 由来のいずれも `tuning_rules` に着地し、同一一覧・同一承認操作・出所が区別できる形で並ぶ。Hermes 固有の UI・テーブル・通知先を作らない | ③ |
| **R7** | **同意を 2 階層に分ける**（D1）。①自テナント内学習（データが R2C の外に出ない）= 既定 ON、②外部 Hermes VPS への生データ提供 = 明示同意必須（既存 `hermes_raw_data_consent` を②の意味に確定）。②の同意操作は旧 UI 閉鎖後も残る場所に置く | ③ |
| **R8** | **Hermes に渡すデータが「コーチに必要な最小十分」になる。** セッション単位・成果（outcome / CV / 離脱）・評価軸・段階を含み、テスト流量を含まない。②の同意テナントのみ | ②③ |
| **R9** | **learned_memory の昇格条件を成果ベースにする**（D2）。Judge スコア単独ではなく、CV / outcome を伴う会話のみを昇格対象にする | ③ |
| **R10** | **到達不能な「学習」コードを処分する。** 救出リストを作り、現行経路へ移植して削除（D5）。ロードマップの完了表記を実態に合わせる | 衛生 |
| **R11** | **学習系 LLM コストが従量課金ポリシー通り計上される**（Judge・gap 推薦・Hermes 分） | ポリシー |
| **R12** | **ページ行動の文脈を学習に載せる**（D7）。会話単体ではなく「どのページで・どんな行動の後に会話が起き・その後どうなったか」を Judge / 効果計測 / Hermes が見られるようにする。情報源は既存 `behavioral_events`。**GA4 は使わない** | ②③ |

### やらないこと

| 区分 | 項目 | 理由 |
|---|---|---|
| OUT | 承認なしの自動適用（プロンプト自動書き換え、承認制ルールの自動有効化） | 「提案→人間承認」が設計上の不変条件（CLAUDE.md 禁止 5）。自動化は R4 の効果計測が安定してから（D2） |
| OUT | **Hermes VPS 側エージェント（プロンプト・cron・MCP ラッパー）の整備** | 横断する相手がいない（§0 前提 2）。R6/R7 で「棚」まで作り、VPS 側は②の同意が取れてから（D3） |
| OUT | **GA4 連携の再生 / GA4 MCP サーバの新設** | 本番の連携テナントが 0 件で、返るのは集計値のためセッションと結合できない。ページ文脈は一次データの `behavioral_events` で足りる（D7）。GA4 の存廃は別件 |
| OUT | Anam 経路の強化 | admin UI から選べず本番 0 件。LemonSlice 経路はテキストと同じ脳なので R1〜R5 が自動的に効く |
| OUT | Hermes 専用の管理画面・ダッシュボード | R6 に反する。インボックスを 5 本目にしない |
| OUT | 新しい学習メカニズム（強化学習、OpenClaw reward 再生、新モデル導入） | 既存 4 系統すら回っていない。増やすより繋ぐ |
| LATER | 承認インボックス 4 系統の統合 UI | R6 で「承認の意味」と着地先を統一すれば、見た目の統合は後から |
| LATER | セッション状態の永続化（PM2 再起動で消える） | R1 の効果を弱めるが単一インスタンス運用の間は致命でない |
| LATER | 商品カードの widget 描画・emotion tag「今なら」撤去・通知リンク修正・set_widget_theme 反映 | 価値はあるが学習ループとは独立。別 PR |

## 4. 成功の定義

「コードが直った」ではなく「ループが回っている」を本番の数字で示す。**判定は暦ではなくセッション数で行う**（D4）。

| 指標 | 現在 | 成功ライン（≈800セッション経過時 / 目安30日） | 要件 |
|---|---|---|---|
| Judge 評価済みセッション / 全セッション | 0 % | ≥ 80 %（離脱含む） | R2 |
| clarify 以外の段階に到達したセッション比率 | 0 % | 商品・価格に言及した会話の過半 | R1 |
| 承認済みだが本番未適用の提案 | 計測不能 | 0 件（承認 = 100 % 適用） | R3 |
| 「あり/なし」比較が出せる承認済み提案 | 0 | 承認済み全件（母数不足は「判定に足りない」と表示） | R4 |
| `prompt_variant_id` が記録されたセッション | 0 | variant を持つテナントで 100 % | R5 |
| 提案の棚 | 4 系統 + UI 無し | Judge / Hermes が同一一覧・同一操作・出所が区別できる | R6 |
| learned_memory の昇格 | 0 件（条件はスコアのみ） | 成果を伴う会話のみが昇格している | R9 |
| 到達不能な学習コード | LangGraph 一式ほか | 0（移植 or 削除）、ロードマップ訂正済み | R10 |
| **北極星**: CV 率 / Judge 平均スコアの推移 | 計測不能 | **計測可能になっていること自体が v1 の成功**。初回判定は ≈1,600セッション（目安60日） | 全体 |

v1 では「CV が上がった」を成功条件にしない。上がったかどうかを知る手段が無いのが問題であり、知れるようになることがゴール。

## 5. 想定されるリスクと落とし穴

**R-1. 「直したつもり」が再発する（最大）**
今回の断線は全て「機能は完成・テストも通る・ロードマップは完了」の状態で起きた。単体テストがモジュール内で閉じ、**経路の端から端までを通すテストが無い**のが根本原因。§7.4 の機械的ガードを必須にする。

**R-9. 単一テナント集中（新規・R-3 を格上げする）**
本番トラフィックの 98% が carnation 1 社。「1 テナントで観察」は実質「全ユーザーで本番投入」であり、段階的ロールアウトの余地が構造的に無い。R1 は自社テナント（r2c_default）とテストチャットで目視確認してから carnation に開ける必要がある（D6）。同時に、carnation で事故ると**本番全体が事故る**。

**R-3. SalesFlow を動かした途端に売り方の品質問題が顕在化する**
propose/close は本番未実行。テンプレ文言・原則注入・緊急性表現が実来訪者に不自然/不誠実に出る可能性。R-9 により影響範囲が全ユーザーになるため、観察期間とテナント単位フラグを DoD に含める。

**R-2. Judge コストの爆発**
離脱セッションを対象にすると評価件数が数十倍（直近30日で 833 セッション）。上限と除外基準が無いと Gemini 費用が先に問題化。従量課金なので上限で止めるのではなく**計上を必ず入れる + 費用が出ることを事前に明示**（CLAUDE.md 禁止 10）。

**R-5. 承認の意味が経路ごとに違う**
`status` と `is_active` の二重管理が今回の P0 を生んだ。どちらが真実かを決めずに両方立てる修正をすると次の追加で同じ事故が起きる（→ G1）。

**R-6. 効果計測の統計的落とし穴**
「ルールあり/なし」比較はルールが当たる会話と当たらない会話の比較になり、そのままでは選択バイアスで無意味。同一トピック内比較かランダム割当にする。数字を出すことより**誤った自信を与えない**ことを優先。

**R-4. Hermes 側がブラックボックス**
提案の質・頻度・プロンプトが不明。ただし D3 により本件では棚を作るまでで止めるため、当面のリスクは「毎日 00:00 に叩いてくる外部プロセスの実体・鍵・停止手段を把握していないこと」に限定される（→ G5）。

**R-7. 死んだ塔に本物が埋まっている**
LangGraph 経路には Judge 発火・avatarPolicy・loopDetector・flowContext など現行経路に無い実装がある。救出リストを作ってから削除する（D5・G4）。

**R-8. 旧 UI 閉鎖との競合**
同意トグルは閉鎖観察中の `/admin/avatar`（〜2026-10-13）にある。R7 の置き場所を copilot ツールにしないと閉鎖で同意経路が消える。

## 6. 制約

### 6.1 3層の役割分担（この境界を破らない）

CLAUDE.md「指示ルールの不変ルール」を本件でもそのまま適用する。学習で生まれた出力を**どの層に置くか**の判断が本件の中心になるため、先に固定する。

| 層 | 役割 | 学習出力の受け皿として |
|---|---|---|
| FAQ / 知識データ（RAG） | **事実の単一情報源** | gap 由来の「知らなかった事実」はここへ。Judge/Hermes の方針提案をここに入れない |
| `tuning_rules.expected_behavior` | **方針**（どう振る舞うか） | Judge / Hermes 提案の既定の着地点（R6）。事実を書かない |
| `tuning_rules.approved_responses` | **文体・言い回しの見本** | 高スコア会話由来の言い回し。逐語コピーを強制しない |
| `learned_memory` | 過去会話の要約知見（RAG 併合） | 唯一の自動経路。**本件では適用範囲を広げず、昇格条件を成果ベースに絞る**（R9） |

### 6.2 統合方針（新規ファイルを安易に作らない）

これはリポジトリの既存規約であり、`copilot-preview/index.test.tsx` に「新規APIを作らない」を機械的に守るテストが既にある。同じ扱いを本件にも適用する。

| 要件 | 変えるもの | 置き場所（ここ以外に作らない） |
|---|---|---|
| R1 | 段階の引き継ぎ | `src/agent/dialog/dialogAgent.ts` の `previousMeta` 受け渡しのみ。遷移判定は既存 `src/agent/orchestrator/sales/salesStageMachine.ts`。第2の遷移表を書かない |
| R1 | 段階の保持 | 既存 `salesContextStore.ts`（`${tenantId}::${sessionId}` キーの正例）。**新しい Map / staging を作らない** |
| R1 | 段階的開放のフラグ | 既存 `tenants.features`。新しいフラグ機構・環境変数を作らない |
| R1 | sales ログ | 既存 `salesLogWriter.ts` の sink を実装。第2のログ経路を作らない |
| R2 | 評価の実行 | `src/agent/judge/judgeEvaluator.ts` の `evaluateSession` のみ。**第2の Judge 実装を作らない** |
| R2 | 定期実行 | `src/index.ts` の既存 `setInterval` 群（pipelineQueue self-heal と同じ場所・同じ形）。cron / launchd / 新プロセスを増やさない |
| R2 R11 | コスト計上 | 既存 `trackUsage`。呼び出しを増やすだけで新しい計上機構を作らない |

| R4 | 効いた要素の記録 | 既存 `chat_messages.metadata`（`rag_hit_count` 等と同じ場所）。**新テーブルを作らない** |
| R4 | 比較の集計 | 既存 analytics のリポジトリ層。週境界・期間計算は `src/lib/date/weekRange.ts` |
| R5 | variant 選択・記録 | `src/agent/ab-test` の `selectVariant`（`sessionId` は既存引数）+ `src/api/chat/route.ts` の既存 `saveMessage` + 既存列 `chat_sessions.prompt_variant_id` |
| R6 | 提案の着地 | 既存 `tuning_rules`（`source='judge' \| 'hermes'`, `is_active=false`）。**`hermes_strategy_proposals` を承認導線として育てない** |
| R7 | 同意の操作 | `toolDefinitions.ts` + `actionExecutor.ts` の case + `copilot-preview/index.tsx` の `REAL_TOOL_LABEL`（**3点セット**）+ `confirmPolicy.ts` の分類。書き込みは既存 `PATCH /v1/admin/my-tenant` |
| R7 | 設定変更の監査記録 | `agentAuditLog.ts` → 既存 `tenant_settings_history`。新テーブルを作らない |

| R9 | 昇格条件 | `src/agent/memory/memoryDistiller.ts` の既存判定。第2の蒸留経路を作らない |

| 全 | DB 列追加 | 機能ディレクトリ内 `migration_<機能>.sql`、`ADD COLUMN IF NOT EXISTS` + `COMMENT ON COLUMN` |

**新規ファイルが許される条件（すべて満たす場合のみ）**

1. テスト可能な純関数として切り出せる（例: 評価対象セッションの選定条件、効果比較の集計ロジック）
2. 既存ファイルに置くと責務が明らかに混ざる
3. **なぜ分けたか・単一化しない理由・既知の未解決事項を冒頭コメントに書ける**（`confirmPolicy.ts` / `agentAuditLog.ts` が基準）
4. 隣に `*.test.ts` を置く

### 6.3 踏襲する既存パターン

| パターン | 実体・先例 |
|---|---|
| 自動生成物は非公開・非有効で投入し、人間承認で公開する | `evaluationAnalyzer.ts` の `is_active = false` 明示 INSERT / 知識の `is_published = false` |
| インメモリ状態は `${tenantId}::${sessionId}` でキー付け | 正例 `salesContextStore.ts`（違反例 `contextStore.ts` は越境リーク実績） |

## 8. 受け入れ条件

### 8.1 着手前ゲート（これを決めるまで実装に入らない）

**G1. 承認状態の単一の真実を決める。**
`status` と `is_active` のどちらを真実とし、もう一方をどう扱うか（廃止 / 派生 / 同時更新の単一関数化）を確定する。既存データの移行方針（現在 `status='active'` だが `is_active=false` の行）も含む。X3 の再発防止のため、未確定のまま R3 に着手しない。

**G2. 評価対象セッションの定義を確定する。**
「離脱」の判定（最終発言からの経過時間）、最低往復数、除外対象（chat-test / e2e / demo / 社内 IP）、1 テナント 1 日あたりの上限。費用に直結するため、テナントへの費用の伝え方もここで決める（X7）。

**G3. 効果比較の方法を確定する。**
「ルールあり/なし」をどう比較するか（同一トピック内 / ランダム割当）、最低母数 N、母数不足時の表示。誤った自信を与えないことを優先する（R-6）。

**G4. LangGraph 救出リストを作る。**
Judge 発火 / avatarPolicy / loopDetector / flowContext のうち何を現行経路へ移すかを列挙し、移さないものは削除対象として明記する（D5）。

**G5. Hermes VPS の実体を把握する。**
毎日 00:00 に `/v1/hermes-mcp/tenants` を叩いている外部プロセスについて、何が動いているか・誰の鍵か・どう止めるかを確認する（読み取り専用）。D3 により整備はしないが、把握しないまま棚だけ作らない。

**G6. 会話とページ行動の結合キーを決める。**
本番実測で `chat_sessions` 1,041 件のうちページ行動が紐づくものは **0 件**、`behavioral_events` の `session_id` 2,345 種のうち会話と一致するものも **0 件**。原因は ① widget の `EventTracker` が独自 `sessionId` を使い会話の `conversationId` と別 ② `chat_sessions` に `visitor_id` 列が無い（metadata にも無い） ③ `/api/chat` は `visitor_id` を受信済み（`route.ts:79`、行動コンテキストに使用）だが `saveMessage` に渡していない。
(a) `chat_sessions` に `visitor_id` を永続化する / (b) EventTracker の `session_id` を会話 ID に統一する / (c) 両方、のどれを採るかを決める。**過去データは復元不可**（キーが存在しない）ことを前提に、いつから結合可能になるかも明記する。R12 はこのゲートに依存する。

### 8.3 リリースゲート（全要件共通）

- **コード品質**: Gate 1（typecheck / oxlint / jest）+ Gate 2.5（Codex review）+ Gate 3（admin-ui typecheck / vitest / build）が緑。`admin-ui/src` を触る PR は Tier S = 手動マージ。main 直コミット禁止（X23）。
- **テスト**: §7.4 の G-a〜G-j をすべて満たす。特に **G-a（端から端まで）**・**G-d（承認 → プロンプト）**・**G-j（フラグ OFF で従来通り）**が無い PR はマージしない。
- **セキュリティ**: `tenantId` の出所が認証済みコンテキストのみ（X14）。新規 SQL に tenant 述語がある。ロール境界の E2E が緑。
- **可観測性**: sweep の実行回数・評価件数・失敗件数・上限到達がメトリクス/ログで確認できる（本文は出さない）。停止がサイレントにならない。
- **本番検証（デプロイ後 72 時間）**: ① 評価件数が 0 から増えている ② 承認済みかつ未適用の行が 0 ③ `prompt_variant_id` の記録が始まっている ④ Judge のテナント別コストが想定内 ⑤ 会話のエラー率・応答時間が悪化していない ⑥ **carnation の会話ログを目視し、売り方が不自然・不誠実になっていない**。いずれか未達なら切り戻す。
- **≈800セッション経過時の判定**: §4 の成功ラインで評価。北極星（CV 率 / Judge 平均スコアの推移）が**計測可能になっていること**を確認する。数値の改善は次フェーズの目標（初回判定 ≈1,600セッション）。

## 9. 決定事項

**D1（同意）= 2 階層に分ける。**
①自テナント内学習（データが R2C の外に出ない）は既定 ON、②外部 Hermes VPS への生データ提供は明示同意必須。既存 `hermes_raw_data_consent` は②の意味に確定。
*根拠:* carnation は実顧客（starter）であり R2C の自社テナントではない（自社は r2c_default）。他社の会話生データを契約なしに外部 VPS へ出せない。かつ横断する相手が現状いない（§0 前提 2）。①により R1〜R5 の価値は同意を待たず carnation に届く。

**D2（自動適用の境界）= learned_memory は自動のまま、昇格条件を成果ベースに絞る（R9）。**
承認制には寄せない。低リスク分類の自動適用は R4 の効果計測が ≈800セッション分溜まってから再検討。
*根拠:* 承認制にすると唯一動いている自動ループを止め、承認者の負荷だけが増える。一方、現在の「Judge スコア ≥80」単独条件のまま Judge が動き出すと、売れていない会話由来の知見が大量に混入する。

**D3（Hermes VPS）= R2C 側の「棚」まで作り、VPS 側の整備はしない。ただし実体は把握する（G5）。**
*根拠:* 横断する相手がいないため投資対効果が最も低い。一方、毎日 00:00 に外部から叩かれている以上、何が・誰の鍵で動き・どう止めるかを知らないままにはしない。

**D4（判定の時間軸）= 暦ではなくセッション数で判定する。**
成功ラインは ≈800セッション（目安30日）、北極星の初回判定は ≈1,600セッション（目安60日）。個別ルールの効果比較は「比較対象ごとに最低 N 件」を条件にする（N は G3 で確定）。
*根拠:* 直近30日で 833 セッション（≈28/日）。粗い比較には足りるが、ルール単位では母数が割れる。

**D5（LangGraph）= 救出して削除（R10）。** 本番経路の切り替えは行わない。
*根拠:* LangGraph スタックはソース約 2,700 行、現行経路は 1,375 行。切り替えは本番経路の総入れ替えであり、実質唯一の実顧客（carnation, ≈28セッション/日）を人柱にする。一方、LangGraph だけが持つ機能は `flowControl.ts` と `langGraphOrchestrator.ts` の 2 ファイルに集中し、Judge 発火は数行。救出コストが圧倒的に安い。

**D6（段階的開放）= R1 はテナント単位のフラグで段階的に開放する。**
r2c_default（自社）+ テストチャットで目視確認 → carnation に開放、の順序を DoD に含める（X22・G-j）。
*根拠:* 本番トラフィックの 98% が carnation 1 社であり、「1 テナントで観察」が実質「全ユーザーで本番投入」になる（R-9）。

**D7（ページ解析の学習）= 一次データ `behavioral_events` を使う。GA4 は使わない（R12）。**
*根拠:* GA4 は本番の連携テナントが 0 件で、`conversion_attributions` 1,148 件は全て `r2c_db` 由来。GA4 が返すのは集計値でセッションと結合できない。一方 `behavioral_events` は本番で稼働中（page_view 2,234 / chat_open 1,441 / chat_conversion 1,187 / idle_time 577 / scroll_depth 67 / exit_intent 27、異なる URL 27）で `page_url` / `referrer` を持ち、一次データとして細かい。ただし現状は会話と結合できていない（G6）。
