# 管理AI原価の課金・可視化 要件定義

**対象**: Copilot UI / AdminAgent（`admin_agent`）をはじめとする「テナントが管理のために使う AI」の原価と課金。
**正本**: このファイル。実装の不変ルールは `.claude/rules/billing.md`、価格の確定値は CLAUDE.md が一次情報。
**起点**: 2026-09-04 の実機照合（`stripeSync.ts` / `costCalculator.ts` / `planQuota.ts` / `agentRoutes.ts` / `toolDefinitions.ts`）。

---

## 0. 決定事項（2026-09-04, hkobayashi）

| # | 決定 | 内容 |
|---|---|---|
| D1 | **課金する** | 管理AIの利用を課金対象にする。R2C が原価を飲む案は不採用 |
| D2 | **遡及訂正は不要** | `stripe_usage_reports` の送信済み行が 0 件。実害が出る前に是正できる |
| D3 | **儲ける** | free_ad はゲートで塞がず、月次上限つきで開放してアップグレード動線にする |
| D4 | **調査済み**（§1-2） | 原価の主因は tool schema の毎ホップ再送。課金設計とは独立に別タスクで削減する |

**この決定から導かれる設計**（詳細は §4）: 課金の**第3次元「管理AIの相談」**を新設し、
単位は**相談1件（会話単位）**、プランの形は**込み枠＋超過**、単価は**テキスト会話の price を流用**する。

## 1. 事実確認（2026-09-04 実機）

| 観点 | 現状 |
|---|---|
| 原価の記録 | **ある**。`agentRoutes.ts` の両経路で `featureUsed:'admin_agent'`（gpt-oss-120b）を計上。`END_USER_FEATURES` 外なのでマージン ×1（原価のみ） |
| 込み枠プラン（standard / growth） | `computeExpectedBilling` の `text_units` は `feature_used IN ('chat','agent_search')` のみ。**Copilot UI 原価は 100% R2C 負担** |
| 純従量プラン（starter / free_ad / enterprise） | `row_units` が「chat 以外の billable 行」を **1行=1単位** で数えるため、**1ターン = 1会話 = ¥20** で請求される計算になっている |
| 価格の採算根拠 | ¥0.11/会話・¥25.9/分・固定費 ¥22,500/月 の3費目のみ。**管理系 LLM 原価という費目が存在しない** |
| テナント向け表示 | 原価内訳に生の文字列 `admin_agent` が出る（`billingApi.ts` の `LABELS` にキーが無く `?? feature` にフォールバック） |
| プランゲート | `FEATURE_MIN_PLAN` に項目なし。free_ad の月次上限はエンドユーザー会話数しか数えないため、**無料テナントの Copilot 原価に天井が無い** |
| `session_id` | `admin_agent` の `trackUsage` は `sessionId` を渡していない（`request_id` に埋め込んでいるだけ）。**現状では会話単位の集計ができない** |

**同じ穴に落ちている他の機能**: `avatar_config_*` / `book_analysis` / `book_structurize` / `premium_avatar_generation` / `admin_guide`。
いずれも `billable=true` かつ `text_units` の対象外＝純従量プランでだけ会話と同単価で混入する。

## 2. 原価の内訳（D4 の調査結果）

`ADMIN_AGENT_TOOLS` をシリアライズして実測した値。

| 項目 | 実測値 |
|---|---|
| ツール数 | **79個** |
| シリアライズ後 | **73,449 bytes / 43,953 文字**（うち日本語 14,748 文字） |
| 推定トークン | **17,000〜23,000 tok** |
| システムプロンプト | 約 1,300〜1,700 tok |

これが `MAX_TOOL_HOPS = 4` の**毎ホップ丸ごと再送**される。したがって **tool schema が入力トークンの約9割**を占める。

| ホップ数 | 入力トークン | 原価（$0.15/1M in・$0.60/1M out） | 円換算 |
|---|---|---|---|
| 1（ツール呼び出しなし） | 約 20,000 | $0.0034 | 約 ¥0.5 |
| 2（標準的な1ツール＋最終回答） | 約 41,000 | $0.0066 | 約 ¥1.0 |
| 4（上限） | 約 85,000 | $0.0135 | 約 ¥2.1 |

**1相談 ≒ 2〜3ターン**とすると **原価 ¥2〜3／相談**。

**含意**: ツール定義の送り方（用途別サブセット送信・description 圧縮）を変えるだけで原価は6〜7割落ちる。
これは課金設計と独立に効くため**別タスクとして起票する**（§3 N5）。
なお本表は静的な見積もりであり、確定値は `usage_logs.input_tokens` の実測（S2）で置き換える。
ただし S1（`request_id` の冪等化）より前の実測値は二重計上で水増しされている可能性がある。

## 3. 本質的に解決すべき課題

### 課題A（表層）— 同じ1機能の扱いがプランによって真逆
Copilot UI の 1 ターンが、Standard では ¥0、Starter では ¥20 になる。
どちらが正しいかを**決めていなかった**ため、両方が同時に実装されていた。D1 でこれを決着させる。

### 課題B（構造・これが本質）— 課金の次元が2つしかなく、それ以外が余り物として落ちる
請求数量の次元は「テキスト会話」と「アバター分」の2つだけ。`row_units` は
**残り全部を 1行=1単位で拾う受け皿**になっており、新しい `feature_used` を足すと、
宣言しないまま自動的にこの受け皿へ落ちる。admin_agent はその第1号ではなく、既に5機能が同じ状態にある。
**admin_agent を個別に直しても、次に足す管理系機能で同じことが再発する。**

### 課題C（製品戦略との衝突）— 主面の利用を、自分で抑制しかねない
Copilot UI は「テナントの操作を会話に移す」主面。ここに従量課金をかけると、製品が最も使ってほしい行動が、
テナントにとって最も避けたい行動になる。D1 で課金すると決めた以上、**この衝突は価格の形で緩和する**
（相談単位・込み枠・込み枠内は数字を出さない）。緩和が効いているかは §7 G6 で判定する。

## 4. 決定した設計

### 4-1. 課金の第3次元「管理AIの相談」

| 項目 | 決定 | 根拠 |
|---|---|---|
| 課金単位 | **相談1件（会話単位）** | テキストが「会話」単位なのと同じ思想。ターン単位は「長く相談するほど高い」となり課題C を悪化させる |
| 数え方 | **`(session_id, JST暦日)` の DISTINCT** | Copilot UI のセッションはリロードを跨いで生き続けるため、`session_id` だけでは月1件に潰れて過少請求になる。暦日で区切ると過大にも過少にもなりにくい。TZ は `getMonthRangeJst` / `weekRange.ts` と同じ作法（process TZ に依存しない） |
| プランの形 | **込み枠＋超過** | 既存のテキスト・アバターと同じ形。表示は `QuotaBar` を再利用し、新しい表現を作らない |
| 単価 | **テキスト会話の Stripe price を流用（新設しない）** | 単価を2箇所に持たない。テナントへの説明が「対話1件 ¥20」で1本化され、LP の表記と課金が揃う |
| free_ad | **月次上限つきで開放**。超過は 403 ではなく正常系の分岐として案内 | アップグレード動線。禁止39（原価が当社負担に反転する経路の上限）も同時に満たす |
| マージン | `admin_agent` は `END_USER_FEATURES` に**入れない**（原価表示は ×1 のまま） | `cost_total_cents` は原価であって請求額ではない。請求は数量 × Stripe price で決まる（禁止48） |

### 4-2. 込み枠の推奨値（Stripe price 作成時に人間が確定させる）

原価 ¥2〜3／相談を基準に、基本料に対する原価比率を約 2.5% に揃えた案。

| プラン | 込み枠 | 込み枠分の原価 | 基本料に対する比率 |
|---|---|---|---|
| free_ad | 30 件/月 | ¥60〜90 | —（R2C 負担。上限で止める） |
| starter | **なし**（1件目から従量） | — | 基本料0円の純従量に枠を与えると無料枠の新設になる（既存 `PLAN_INCLUDED_QUOTAS` の思想と一致） |
| standard | 100 件/月 | 約 ¥250 | 2.6% |
| growth | 300 件/月 | 約 ¥750 | 2.5% |
| enterprise | 個別 | — | 自動化しない |

### 4-3. 確認が必要な連動点

- **Starter の 480単位キャップ**（`STARTER_MONTHLY_BILLED_QUANTITY_CAP`）は、テキスト会話と管理AIの相談の
  **合計**に掛かることになる。この解釈でよいかを確定させる。
- **`stripe_usage_reports.dimension`**: 画面では別バーとして見せるため次元は分けて記録するが、
  送信先 price はテキストと同じ。請求書上は1行に合算される（＝「¥20/件に揃える」の意図どおり）。
- **LP の表記**: 「¥20/対話」に管理AIの相談が含まれることを明記する。表記と課金は同じ PR で変える（禁止54）。

## 5. ユーザーが本当に得たい価値

| 誰 | 表面上の要求 | 本当に得たい価値 |
|---|---|---|
| テナント（店主） | 「請求の内訳が知りたい」 | **金額を気にせず管理AIに相談できること**。相談のたびに単価を意識させられないこと。請求書を見て驚かないこと |
| R2C 運用者 | 「原価を計上したい」 | **どのテナントが・どの機能で・いくら溶かしているかが1画面で分かり、値付けの判断材料になること**。粗利が黙って侵食されないこと |
| 両者共通 | — | **見えない請求と見えない持ち出しが、どちらも存在しないこと** |

**判断基準**: 「テナントが Copilot UI を使う回数が減る施策は、どれだけ採算が改善しても失敗」。
課金すると決めた以上、この基準は成功条件 G6 として明示的に測る。

## 7. 成功の定義

**前提**: 当面は母数が小さい。母数不足のときは比率・矢印・「効果あり」を出さず、到達条件を出す。

| # | 成功条件 | 判定方法 |
|---|---|---|
| G1 | 管理系原価が**費目として存在**し、テナント別・月次で引ける | 運用者面で任意の1テナントの当月管理系原価が表示できる |
| G2 | 同じ1相談が、**どのプランでも同じ数え方**になる | starter と standard の同一利用が同じ単位数になることをテストで固定 |
| G3 | LP の価格表記と実課金が**一致**する | 「¥20/対話」に管理AIの相談が含まれることが LP に書かれ、実際にその単価で請求される |
| G4 | 新しい `feature_used` を足したとき、**次元を宣言しないとテストが落ちる** | 意図的に未宣言の feature を足して赤くなることを確認 |
| G5 | 再送・二重クリックで `usage_logs` の行が**増えない** | 同一操作の2回実行で行数が1のままであることを固定 |
| G6 | テナントの Copilot UI **利用回数が減っていない** | 施策前後の月次相談件数。減っていたら採算が改善していても失敗 |
| G7 | 監視が**対象0件のときに沈黙しない** | 0件が「正常」か「計上が壊れた」かを区別して鳴る |
| G8 | 請求が**1周する** | テストモードで `stripe_usage_reports.status='sent'` と請求書の確定まで通す。「テストが緑」で完了としない |

## 8. UI／UX 要件

### 原則: 込み枠内は黙り、境界が近いときだけ話しかける

課金すると決めた以上、利用量を常時可視化すると「相談したら課金される」と学習し、主面の利用が減る（課題C）。
一方で何も出さないと「気づいたら請求」になる。したがって **非対称に出す**。

- **込み枠内**: 管理AIの利用件数・原価を**テナント面で前面に出さない**。課金画面に行けば残量は見えるが、
  Copilot UI が自分から件数を報告しない。
- **境界が近い／超えた**: そのときだけ、到達条件と次の行動を出す。「使いすぎ」という語彙を使わない。
- **運用者面**: 常時・全量。判断の主戦場はこちら。

### 面ごとの要件

| 面 | 対象 | 要件 |
|---|---|---|
| `/admin/billing` QuotaSection | テナント | **第3の `QuotaBar`「管理AIへの相談」を追加**。既存部品をそのまま再利用し、独自表現を作らない |
| Copilot UI `billing_summary` カード | テナント | `quota` に管理AIの次元を追加。ただしカード側から件数を能動的に報告しない（込み枠内は残量表示に留める） |
| `/admin/billing` 原価内訳 | テナント | **内部語を出さない**。`admin_agent` →「管理AIへの相談」等を `LABELS` に持つ。未知キーが生の英語で出る現状は命名ルール違反 |
| 同 金額表示 | テナント | USD を整数丸めしているため少額が全て `$0` になる。管理系は少額が常態なので、**0 と「0未満」を区別できる表示**にする。単位は混ぜない（禁止48） |
| free_ad の上限到達 | テナント | 403 のエラー語彙で描画しない。**正常系の分岐**として、残り件数・リセット日・プラン変更の導線を出す。1会話1回（禁止11） |
| 運用者面（tenant-economics / monitoring） | super_admin | テナント別 × 機能別に管理系原価を引ける。粗利に対する比率は**母数条件を満たすときだけ**出す |
| 通知 | super_admin | 異常消費の閾値超過時のみ。テナント宛には出さない。同一テナント・同一期間で1回 |

### 文言の要件

- 管理AIに対して「使いすぎです」「上限に達しました」を使わない。**制限ではなく状態**として書く。
- 未使用テナントの空状態にエラー語彙・❌ を使わない（正常な状態であって故障ではない）。
- 「相談1件」の数え方（同じ相談を続けても1件、日をまたぐと別の1件）を、テナントが読んで分かる言葉で1箇所に書く。

## 9. 主なリスクと落とし穴

| # | リスク | なぜ危険か | 対策 |

## 10. 進め方（ゲート）

```
S1 request_id 冪等化 + session_id の受け渡し
```
