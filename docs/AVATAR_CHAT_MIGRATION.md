## 0. 決定事項（これを前提として要件を組む）

| # | 論点 | 決定 |
|---|---|---|
| 1 | 対象範囲 | **テナントがアバターを作る／運用する管理側フロー**。ウィジェット側（PiP・LiveKit接続ライフサイクル）は対象外 |
| 2 | 主対象ユーザー | **client_admin のセルフサービス**。super_admin の代行構築は主目的にしない |
| 3 | プラン未契約テナントの扱い | **会話上のアップセル導線として見せる**（入口を塞がない） |
| 4 | 旧UIアバターページの終期 | **最終的に閉じる対象**とする。`LEGACY_UI_SUNSET.md` §9・§4 の「クローズ対象外」分類を撤回する |
| 5 | ライブテストの離脱 | **初期は離脱1回を許容する**。`/admin/chat-test` への受け渡しを恒久的な正常状態とみなす |

決定4が本書で最も効く。アバターは現在 `LEGACY_UI_SUNSET.md` §9 で「Legacy-link-only（GUI固有・クローズ対象外）」に分類されている唯一の主要設定機能であり、**この分類の撤回自体が最初の成果物**になる（§5）。

## 1. 現状（実測）

### 1.1 チャット側にあるもの

| 対象 | 実測 |

| 画面 | 内容 |
|---|---|

### 1.3 現状分類

`LEGACY_UI_SUNSET.md` §1.2-9 および §4 の「クローズ対象外」表は、アバターを「見て・聴いて選ぶ操作はテキスト往復に写像できない」として**恒久残存**に分類している。

> ただしこの表の判定は **すでに1件覆っている**。同じ表で「PDFアップロードはファイル選択という GUI 固有操作」とされていた知識データPDFは、#585 でコンポーザへの添付（📎/ドラッグ＆ドロップ）＋ `pdfUpload` カードにより**会話内完結**へ移された。「GUI固有」は操作の様式に対する記述であって、面の外に置く理由としては十分ではない、というのが実装で示された先例である。
>
> **ただし #585 を引くのは実装機構（コンポーザ添付＋進捗カード）についてのみである。** 書籍/PDFナレッジは 2026-07-31 の決定により**テナントには投入導線を出さない**方針となったため、「テナント向けにファイル投入をチャット化した」という導線方針の先例としては引かない。アバターの音声クローン素材はテナント自身が用意するものなので、この制約とは衝突しない。

## 2. 本質的に解決すべき課題

1. **チャット側の動線が構造的に閉じていない。**
   `activate_avatar` は `id` 必須だが、**候補一覧を返すツールが存在しない**。`get_avatar_status` は稼働中の1件しか返さないため、ユーザーは旧UIで id を確認してこない限り切替できない。決定4により旧UIを閉じると、**切替手段そのものが消える**。現状のチャット側アバター機能は事実上、動線として成立していない。

2. **「見て・聴いて決める」を面の外に置いたままでは、原理的に閉じられない。**
   実際に視聴覚が要るのは **画像候補の採否 / 声の試聴採否 / ライブテスト** の3点だけである。名前・性格・口調・どれを出すか・止めるかはすべてテキストで決まる。3点を理由にフロー全体を旧UIへ押し出している現状は、判断の粒度と操作の様式を取り違えている。

3. **セルフサービス（決定2）なのに「ゼロから作る」を強いている。**
   ウィザードは6ステップ×多数の選択肢。専門知識のない店舗管理者にとって、選択肢の多さは自由ではなく負担である。

4. **画像生成が使用量に計上されず、請求できていない（実測。2026-07-31 修正）。**
   生成コストは従量課金でテナントに請求される設計である（`avatar_config_image` は `NON_BILLABLE_FEATURES` に含まれず billable = true、マージン ×1 の管理機能扱い）。したがって**回数上限は不要**で、必要なのは正しく計上することである。

   - 通常生成 `/v1/admin/avatar/fal/generate` は **`trackUsage` を呼んでいない**（`falGenerationRoutes.ts`、grep 0件）。4枚生成の原価が `usage_logs` に載らず、**当社が被って請求できていない**
   - 計上済みは `generationRoutes.ts:224`（generate-image）/ `premiumGenerationRoutes.ts:262` / `routes.ts:863`
   - `/admin/avatar` はサイドバーに**プランゲート無しで全admin可視**（`AppSidebar.tsx:77`）。プランゲートがあるのは `generate-premium`（`premium_avatar`）、`voice-clone`（`voice_clone`）、`activate_avatar`（`avatar`）の3つだけ

   つまり Starter テナントは**画像を生成できるが公開はできない**。これは決定3（アップセル導線）のもとでは**意図した体験**であり、従量課金なので生成分は請求できる。ただし計上されていない現状ではその請求が発生していない。

## 3. ユーザーが本当に得たい価値

> 「うちの店の顔を、迷わず、10分で、恥ずかしくない状態で出したい」

欲しいのはアバターそのものではなく、**接客担当が表に立っている状態**である。

| 価値 | 設計上の含意 |
|---|---|
| **選ばせない** | 既定アバター（`/admin/avatar-defaults` の資産）＋業種から**先に1案を出す**。ゼロからの生成は「気に入らなかった人」の分岐であり、主経路ではない |
| **差分だけ直せる** | 「もう少し若く」「もっと落ち着いた声で」を会話で受ける。全項目のフォームを見せない |
| **出す前に確認できる** | 採否の瞬間（画像・声・実挙動）だけ視聴覚。うち画像・声は会話内カードへ、実挙動はライブテストへ（決定5） |
| **すぐ止められる** | 無効化・切替・既定に戻すが会話で完結する |

## 4. スコープ

### 4.1 やる — 3層に分ける

| 層 | 内容 | 最終形 |
|---|---|---|
| **A. 会話で完結（テキスト）** | 設定一覧（id/名前/状態/サムネ）・状態確認・有効化・**無効化**・切替・名前/性格/口調の更新・既定に戻す・業種からの推奨提示 | チャットのみ |
| **B. 会話内に埋め込むGUI部品** | 画像候補カード（サムネ＋「これにする」チップ）／音声試聴カード（プレイヤー＋採否チップ）／クローン音声の添付（**PDF と同じコンポーザ添付方式**、#585 の実装をそのまま踏襲） | チャット内カード。専用ページを作らない |
| **C. 面の外に残す** | **ライブテスト**のみ | `/admin/chat-test` へ受け渡し（`LEGACY_UI_SUNSET.md` §11 でクローズ対象外が確定済み）。決定5により離脱1回を正常とみなす |

**層Aが先。** 一覧ツールが無い限り `activate_avatar` は今も将来も使えない（§2-1）ため、これが単独で最優先である。

### 4.2 やる — 閉鎖のための前提整備

5. **`LEGACY_UI_SUNSET.md` の分類改訂**（§5 に差分案）。これをやらないと、アバターだけが閉鎖判定基準の外に居続ける。
6. **アップセルの明示的設計** — 未契約テナントは推奨案の提示・生成・プレビューまで到達でき、**有効化のところで初めて**プラン案内が出る。#580（プラン制限の案内を会話内で繰り返さない）に従い **1会話1回**。同時に生成回数の上限を入れる（現状 `fal/generate` は無制限）。
7. **計測** — 面識別は #588 で入った。その上でアバター専用ファネル（推奨提示→生成→採用→有効化→ウィジェット露出→継続率/CV）を定義し、閉鎖判定 C1〜C4 をアバターページにも適用可能にする。

### 4.3 やらない

- 旧UIページ（`/admin/avatar`, `/wizard`, `/studio`）の**先行削除** — 閉鎖は判定基準の充足後。順序を逆にしない
- **パネル（Surface A）への移植** — `CHAT_SURFACE_DECISION.md` 推奨(c)により機能凍結中。アバターUIをパネルに入れない
- ウィジェット側の PiP／LiveKit 接続ライフサイクル変更（`PIP_AVATAR_PERSISTENCE_DESIGN.md` の別タスク）
- 生成モデル・感情タグ・音声プロバイダの刷新（表現品質そのもの）
- `/admin/avatar-defaults`（super_admin 専用）のチャット化 — 決定2により対象外。ただし既定アバターを**素材として読む**のは層Aに含む
- ライブテストの会話内埋め込み（決定5）— 離脱0は閉鎖の必要条件ではない
- 単一セッションキー化（`CHAT_SURFACE_DECISION.md` §5補記で、メッセージ表現共通化が前提と決定済み）

### 4.4 目標状態のフロー

```
① 「アバターを出したい」／レール「アバター」
   → 状態を返す（未作成 or 稼働中の設定名）
② 未作成なら: 業種・雰囲気を1〜2問だけ聞く
   → 既定アバター＋業種から【推奨1案】をカードで提示（この時点では生成しない）
③ 「これでいい」→ 採用／「もう少し◯◯」→ 差分を受けて候補カードを再提示
   （ここで初めて生成APIを叩く。生成のたびに従量課金が発生する旨を伝える）
④ 声: 試聴カード＋採否チップ。自前の声を使うなら添付でクローン
⑤ 名前・性格・口調をテキストで確定 → 保存
⑥ ライブテストへ受け渡し（唯一の離脱）→ 戻って「これで公開する」
   → 有効化（未契約ならここでアップセル案内 1回）
```

離脱は⑥の1回のみ。これが C4（チャットが迷路になっていないこと）に対する設計上の答えになる。

## 5. `LEGACY_UI_SUNSET.md` への差分案

決定4を反映するために必要な改訂は4点。**うち3点は判定基準の適用方法に関わるもので、分類の書き換えだけでは足りない。**

### 5.1 §1.2-9 の分類変更

- 現行: `#### 9. アバター設定 /admin/avatar — Legacy-link-only (GUI固有・クローズ対象外)`
- 改訂: `#### 9. アバター設定 /admin/avatar — Chat-partial（Wave 3・チャット側の実装後に計測開始）`
- 「GUI固有として恒久的に残る想定」の段落を削除し、§4.1 の3層（会話で完結／会話内カード／ライブテストのみ外部）と決定5を記述する。

### 5.2 §4「クローズ対象外」表からの除去と Wave 3 の新設

アバター行を対象外表から外し、Wave 2 の後ろに **Wave 3** として置く。Wave 2（ダッシュボード・会話履歴）が「ツールを1つ足す→計測」で済むのに対し、アバターは層A＋層Bの実装を伴うため、同列に置くと Wave 2 の軽さが失われる。

### 5.3 母集団の定義（§2.2 への追記）— **決定3の副作用**

`/admin/analytics`・`/admin/conversion` と異なり、アバターページは**プランに関係なく全 client_admin に見えている**（`AppSidebar.tsx:77`、§2-4）。さらに決定3により、Starter テナントも意図的にフローへ入れる。

したがって:

- **C1・C2 の母集団は `avatar` プラン保有テナント（Growth+）に限定する。** Starter のターンを分母に入れると比率が薄まり、「使われていないページ」と誤判定される（§2.2 が analytics/conversion について述べているのと同じ理由）。
- **Starter テナントの会話は閉鎖判定に使わず、アップセル指標（§6）で別に測る。** 有効化まで到達できない母集団を閉鎖判定に混ぜてはならない。

### 5.4 低頻度ページであることの扱い — **C2 の抜け穴**

アバターは `/admin/engagement` と同じく「一度設定したら触らない」低頻度機能である。ここで既存基準に2つの穴がある。

1. **C2（代替比 20:1）は handoff が 0 に近づくと自明に成立する。** 層A・層Bを入れて `avatar_wizard`/`avatar_studio` の handoff が消えれば、分子が月数件でも比率は満たされてしまう。§2.3 の注記「C2 は『使われていないから閉じられる』を排除する条件でもある」が、低頻度ページでは機能しない。
2. **C2b（テナント1社あたり週1.0件）は原理的に満たせない。** `/admin/engagement` に与えられた例外（8週窓 + 新規テナント限定）と同じ扱いが必要になる。

したがってアバターには、C1〜C4 に加えて **ファネル完了率**（§6 の一次指標）を実使用証拠として要求する。「触られていないから閉じてよい」と「チャットで完了できているから閉じてよい」を区別できる指標は、低頻度ページではこれしかない。

### 5.5 C1 の分子から `chat_test` を除外する（決定5の帰結）

Stage B で削除するのは `avatar_wizard` / `avatar_studio` の2キーのみ。**ライブテストへの `chat_test` handoff はアバターのフローの正常な一部**であり（決定5）、これをアバターの C1 の分子に含めると、アバターページは恒久的に閉じられなくなる。C1 は `feature ∈ {avatar_wizard, avatar_studio}` のみで測ると明記する。

## 6. 成功の定義

| 層 | 条件 |
|---|---|
| **閉鎖ゲート（最終目標）** | `/admin/avatar` 系3ルートが §5 改訂後の基準（C1〜C4 + ファネル完了率、8週窓・新規テナント限定・Growth+ 母集団）を満たしてクローズできること。これが唯一の「終わった」の定義 |
| **一次（体験・実使用証拠）** | 新規テナントのうち、**チャット経由で有効化まで到達した割合**／所要 ≤10分／チャットを離れる回数 ≤1回（ライブテストのみ） |
| **二次（動線）** | チャット経由の `activate_avatar` が実際に発生すること（**現状は構造上ほぼ0のはず。ベースライン計測が着手1件目**）／推奨1案がそのまま採用される率（＝「選ばせない」設計が効いているか） |
| **三次（事業）** | アップセル案内→プラン変更のCVR／アバター有効テナントの継続率・CV改善（既存A/B基盤 #561、露出計測 #565） |
| **反証条件** | 推奨1案の採用率が低く再生成回数が多い場合、「選ばせない」仮説が誤り。テナントの請求だけが増えるため、候補一覧を先に見せるGUI的な提示へ戻す |

## 7. リスクと落とし穴

1. **課金漏れと、テナントの請求が意図せず膨らむこと（実測済み・最優先）** — `fal/generate` が `trackUsage` を呼んでおらず、生成の原価が請求されていない（§2-4）。まずこれを塞ぐ。そのうえで、従量課金である以上、会話化して「もう1回作って」の心理的コストが下がると**テナントの請求が本人の意図より膨らむ**。回数上限で止めるのではなく、**費用が発生することを生成の前に伝える**（確認ゲート）ことで守る。
2. **手書きコピーの再生産** — カード／コンポーザを新規実装すると、`CHAT_SURFACE_DECISION.md` §3.1 の IME 事故（正しい実装が同リポジトリに1ヶ月あったのに再利用されず、日本語入力が約13日壊れた）と同じ再発条件を作る。共有層（`useAgentChatTransport` / カードチャネル #578 / PDF添付の実装）に載せることが着地条件。
3. **認可** — `/v1/admin/avatar` 系は過去に3ルートの認可欠落実績（PR #209）。テナント越境（#564 と同型）と、super_admin の `targetTenantId` 導出が2箇所別実装（`CHAT_SURFACE_DECISION.md` §1.9、未解消）に毎回触れる。
4. **同意・権利** — 音声クローン素材の権利、実在人物に似た生成物。GUIならセクションとして明示できるが、**会話では同意が対話の流れに埋もれる**。同意は会話ターンではなくレコードとして残す。
5. **下書きの孤児化** — 生成候補を `(tenantId, sessionId)` 型の一時ステージングに置くと `knowledgeImportStaging` と同じ穴（面をまたぐ／リロードで30分TTL失効）を再生産する。**最初から `avatar_configs` の永続実体に置く**。
6. **アップセルが押し売りになる** — #580 の修正意図（案内を繰り返さない）を壊すと、未契約テナントの会話がプラン案内で埋まる。案内は**有効化の瞬間だけ・1会話1回**。
7. **「閉じる」が宣言だけで終わる** — §5 の改訂を入れないまま層A/Bを実装すると、旧UIは残り二重メンテだけが増える。**分類改訂を実装の前提タスクにする**。
8. **使えないツールを増やす** — 現状の `activate_avatar`（一覧なし）と同型の失敗。ツールは**動線として閉じた単位**でしか足さない。

## 8. 着手順（推奨）

| 順 | 内容 | 理由 |
|---|---|---|
| 1 | ベースライン計測（チャット経由の `activate_avatar` / `avatar_*` handoff の現在値） | 「改善した」を言うための基準線。現状ほぼ0であることの確認も含む |
| 2 | `LEGACY_UI_SUNSET.md` の §5 改訂 | 以降の実装がクローズパスに乗るための前提 |
| 3 | 層A（一覧・無効化・テキスト更新・既定に戻す） | これ単体で `activate_avatar` が使える機能になる |
| 4 | 生成の使用量計上（課金漏れ）の解消（§2-4） | 層Bで生成を会話から叩けるようにすると未計上の生成が増えるため、先に塞ぐ |
| 5 | 層B（画像候補カード → 音声試聴カード → クローン添付） | 共有層に載せる。カードは #578 の `card` チャネルを使う |
| 6 | ファネル計測 → 8週窓で判定開始 | §6 |

## 9. 本要件が誤りだと判明する条件

- **推奨1案の採用率が低い場合** — 「選ばせない」前提が崩れ、層Bは候補一覧の提示UIとして作り直しになる。
- **チャット経由の完了率が旧UIウィザードを下回る場合** — 決定4（閉じる）の前提が崩れる。その場合はアバターを対象外分類へ戻し、GUIとしての作り込みに投資するのが正しい。
- **アバター有効化がCV改善に繋がらないことがA/Bで示された場合** — フローの改善ではなく、機能そのものの位置づけの見直しになる。

# 制約

## 10. 実装上の制約

### 10.1 既存コードへの統合方針（新規ファイルを安易に作らない）

**原則: 増やすのは「ツール1本 = `toolDefinitions.ts` への定義追加 + `actionExecutor.ts` への case 追加 + `TOOL_LABELS` への日本語ラベル追加」の3点セットのみ。** 新規ファイル・新規エンドポイント・新規ページはいずれも既定では作らない。

| 関心事 | 置き場所（既存） | 新規作成の可否 |
|---|---|---|
| HTTP API | `src/api/admin/avatar/routes.ts`（configs CRUD / voice-clone / reset-to-default）、`generationRoutes.ts`、`falGenerationRoutes.ts`、`premiumGenerationRoutes.ts` | **不可**。層A・層Bで必要な操作はすべて既存エンドポイントで足りる。新規エンドポイントを足す前に、既存で満たせない理由をPR説明に書く |
| エージェントのツール定義 | `src/api/admin/agent/toolDefinitions.ts` の `ADMIN_AGENT_TOOLS` | 追記のみ |
| ツールの実行 | `src/api/admin/agent/actionExecutor.ts` の `executeToolCall` switch | 追記のみ。共通ロジックが複数caseから使われ50行を超える場合に限り `src/api/admin/agent/` 配下へ切り出す（前例: `engagementSuggest.ts` / `industryFaqTemplates.ts` / `knowledgeImportStaging.ts`） |
| 有効化の実処理 | `actionExecutor.ts:84` の `activateAvatarConfig`（既存・エクスポート済み） | 再利用する。同等処理を別実装しない |
| チャットUI | `admin-ui/src/pages/copilot-preview/index.tsx` | 追記のみ。**アバター専用ページ／ルートを新UIに作らない**（§4.3） |
| 送信・履歴・テナント導出・エラー文言 | `admin-ui/src/lib/useAgentChatTransport.ts` | **必ず経由する**。`authFetch` の直書き禁止 |
| 会話の永続化 | `admin-ui/src/lib/chatSessionStore.ts`（面ごとキー） | アバター専用ストアを作らない |
| ファイル添付 | コンポーザの📎/ドラッグ＆ドロップ + `lib/bookPdfUpload.ts` 相当の検証 + `pdfUpload` カードの進捗表示 | **既存機構を拡張**。第2の添付経路を作らない |
| 構造化カード | `actionExecutor.ts` の `ActionResult = string \| { text; card? }`（#578）と `useAgentChatTransport.ts` の `AgentActionCard` | union にバリアントを追加。**自然文の正規表現パーサを新規追加しない** |
| 生成候補・下書きの保持 | `avatar_configs` テーブル（実体） | プロセス内Map（`knowledgeImportStaging` 型）を新設しない（§7-5） |

**カードは必ずサーバの `card` チャネルで返す。** `copilot-preview/index.tsx` には `parseSuggestFaq` など自然文を正規表現で読む4本のパーサが残っているが、これは #578 以前の経路であり**フォールバック契約として残っているだけ**である。新しいカードで5本目を足すと、ツールの文言を変えるたびにカードが黙って消える経路を増やすことになる。

### 10.2 守るべき設計原則・命名規則・既存パターン

**ツール命名** — 既存45本の規約に従う（snake_case、動詞_目的語）。読み取り `get_*` / 一覧 `get_*_list`・`list_*` / 下書き提示 `suggest_*` / 確定書き込み `save_*`・`update_*`・`delete_*` / 状態切替 `activate_*`・`dismiss_*`。

**リスク階層への登録は必須（テストが機械検出する）**
- 新ツールは `src/api/admin/agent/confirmPolicy.ts` の `WRITE_TOOL_RISK_TIERS` か `NON_WRITE_TOOLS` の**どちらかに必ず入れる**。`confirmPolicy.test.ts` が「全ツールが分類表のいずれか一方だけで数え上げられる」を件数一致で検証している。
- 階層の当てはめ（`confirmPolicy.ts` の定義に従う）: 画像生成・プレミアム生成・音声クローンは**課金が発生する**ため `high`。性格・口調・名前の更新は永続コンテンツの変更で `medium`。有効化／無効化はフラグ切替で `low`（既存の `activate_avatar` と同じ）。
- executor で**新しい書き込みヘルパ関数**を使う場合は `confirmPolicy.test.ts` の `MUTATION_PATTERNS` にも追加する。この配列と実装側の書き込み一覧は**厳密一致**で検証されるため、追加漏れはテストが落ちる。

**ツール結果文字列の規約**
- 500字以内の日本語（`truncate`）。技術的詳細を出さず、次の行動を伝える。
- **確認ゲート以外の文脈で「確認が必要です」「確認をスキップできません」を含めない。** `AGENT_METRICS.md` の `agent_tool_invoked` は結果文字列の部分一致で `outcome` を判定するため、含めると正常応答が `blocked` として計上される（`get_embed_code` で実際に踏みかけた罠）。
- 逆に確認ゲートの文言は既存の「〜には確認が必要です」の形を保つ。フロント側のチップ表示条件（`index.tsx` の `saiPendingConfirm` 等）も同じ部分一致に依存している。

**認可・テナント境界**
- 既存の `extractAuth` / `isAllowedAvatarRole` / `denyAvatarRole` を踏襲する。
- **client_admin は JWT の tenantId を必ず使い、`tenant` クエリでの上書きは super_admin のみ**（`routes.ts:362-378` の Bug-3 fix と同じ形）。
- プランゲートは注入済み `db` を使い `queryTenantPlan` + `planHasFeature` で判定する。`tenantHasFeature` は内部で `getPool()` を呼ぶためテストのモックPoolと食い違う（`activate_avatar` の既存コメントが理由を記録している）。

**計測**
- 計測は `agentRoutes.ts` にのみ実装する。`actionExecutor.ts` の case には**メトリクスを書かない**（`AGENT_METRICS.md` §実装上の制約）。
- 記録は fire-and-forget。計測の失敗が応答のステータスや本文を変えてはならない。

**フロント**
- 新ツールは `copilot-preview/index.tsx` の `TOOL_LABELS`（47件）に必ず追加する。漏れると生の英語ツール名が画面に出る（パネル側が9件で取り残された事故と同型）。
- 文言はハードコード日本語のまま。この画面は i18n 層を持たない（`LangSwitcher` はあるがチャット本文は対象外）ので、ここで翻訳機構を導入しない。
- 会話・下書きは **sessionStorage 限定**（`chatSessionStore.ts` の決定。共有端末に個人情報を残さないため）。localStorage を使わない。

### 10.3 やってはいけないこと

1. **判定前に旧UIのアバター画面を消す／リダイレクトする**（§5・§6 の順序を逆にしない）
2. **パネル（Surface A）にアバターUIを足す** — `CHAT_SURFACE_DECISION.md` 推奨(c)により機能凍結中
3. **新UIにアバター専用ページ／ルートを作る** — 会話の中に置くことがこの移行の目的
4. **自然文パーサを5本目として足す** — カードは `card` チャネル（10.1）
5. **IME/Enter の送信判定を独自実装する** — 既存コンポーザを使う。手書きコピーは §7-2 の再発条件
6. **`chat_test` handoff をアバターの C1 分子に含める** — 決定5により恒久的に閉じられなくなる（§5.5）
7. **費用が発生する操作を、費用が出ると伝えないまま会話から叩けるようにする／使用量を計上しないまま外部APIを呼ぶ** — §7-1
8. **`is_active = true` だけで「稼働中」と判定する** — 既定アバター（`tenant_id = 'r2c_default'`、18体）は部分unique制約から除外されており**全て `is_active = true`** である。稼働中の判定は必ず `tenant_id = <対象テナント> AND is_active = true`
9. **super_admin の previewMode で `targetTenantId` を無視した書き込み経路を作る** — 越境（#564 と同型の事故）
10. **音声クローン素材の同意を会話ターンだけで済ませる** — 同意はレコードとして残す（§7-4）
11. **生成候補をプロセス内のステージングに置く** — `knowledgeImportStaging` の孤児化を再生産する（§7-5）
12. **`pnpm verify` を通さずに出す** — oxlint は `--max-warnings 63` で上限が固定されているため、警告を1件増やすだけで落ちる
