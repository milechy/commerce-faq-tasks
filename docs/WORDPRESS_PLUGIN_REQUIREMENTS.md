## 0. 決定事項（着手前に確定済み）

| # | 決定 | 理由 |
|---|---|---|
| **D1** | **配布は wordpress.org 公式ディレクトリを優先**する。自社 zip 直配布は当面やらない | 発見性と信頼性。ただし後述の全ガイドライン適合が出荷条件になる |
| **D2** | **接続はプラグイン内サインアップ**（WP 管理画面からメール入力 → R2C テナント自動作成 → キー自動設定） | 導入摩擦の最小化。ただし**サーバ側に公開プロビジョニング API が存在しないため新規実装が必要**（§5） |
| **D3** | **v1.0 のスコープはウィジェット設置＋設定のみ**。WP 記事の知識源同期・WooCommerce 連携は v1.1 以降 | 最短で審査を通し、審査リスクを最小化する |
| **D4** | **slug は `r2c-ai-concierge`**、表示名は `R2C – AI Concierge & Chat for Customer Support`。タグは `chatbot` / `live chat` / `ai` / `customer support` / `faq` の 5 個 | 2026-09-04 実測で `r2c` / `r2c-chat` / `r2c-ai-concierge` / `rajiuce` / `ai-concierge` / `r2c-widget` はいずれも未使用。`r2c` 単体は 3 文字で検索に埋もれ他社の同名略称と衝突しやすく、`rajiuce` は英語圏で読めない。GL#17（他者商標を slug 先頭に置かない）・GL#12（タグ 5 個上限）を同時に満たす |
| **D5** | **利用規約 `https://r2c.biz/legal/terms.html` / プライバシーポリシー `https://r2c.biz/legal/privacy.html` を readme に記載する** | 両 URL とも到達可能（200）。ただし**中身が未記入のままであり、埋めるまで提出できない**（§10 B-1） |
| **D6** | **API キーはローカルで暗号化しない。** `wp_options` に `autoload = false` で保存し、**キーのスコープ限定・ドメイン束縛・マスク表示・即時失効**の 4 点で守る | `AUTH_KEY` 由来の暗号化は鍵が同じ `wp-config.php` にあるため実効性がなく、監査でセキュリティシアターと見なされる。スコープ限定（chat のみ / 管理 API 不到達）と `allowed_origins` 束縛により、漏洩時の最悪ケースを「そのドメインでチャットが呼べる」に限定できる。両方とも既存機構で実現可能 |
| **D7** | **`free_ad` 総量ガードの初期値は「同時 100 テナント / 新規 30 件・日」、原価アラートは「`free_ad` 全体の当月原価 ¥20,000」** | 固定費が月 ¥25,655 に対し `free_ad` 枠を月 ¥30,000 と置く。上限張り付き時の 1 テナント最悪値は管理 AI ¥60〜90（`docs/ADMIN_AGENT_COST_REQUIREMENTS.md` の実数）＋会話 200 件分で月 ¥300〜500 と**見積もり**（会話単価は `costCalculator.ts` のモデル別のため推定値）。最悪値ベースで 60 件、実際は上限張り付きが稀なため初期値 100 件。アラートは枠の手前で鳴らす |
| **D8** | **プラグインは専用リポジトリ `milechy/r2c-wordpress-plugin` を新設し GPLv2 で公開**する。本リポジトリには置かない | wordpress.org が求めるのは開発リポジトリへのリンクのみでサーバコードの公開は不要（GL#4）。本リポジトリに GPLv2 のディレクトリを混ぜるとライセンス境界が曖昧になる。SVN 同期スクリプトの置き場としても独立が望ましい |

## 1. 目的

R2C の AI 接客ウィジェットを、**WordPress サイト運営者が管理画面から数クリックで導入できる**ようにする。
現状の導入経路は「テナント登録 → 管理画面で API キー発行 → HTML に 1 行貼り付け」であり、
テーマファイル編集を伴うため WordPress 利用者層にとって障壁が高い。

**成功の定義（v1.0）:**

1. wordpress.org 公式ディレクトリに掲載されている
2. WP 管理画面のみで、テーマファイルを一切編集せずにウィジェットが稼働する
3. プラグイン有効化から稼働までの所要時間が **5 分以内**

### 2.1 審査プロセスの前提

- **Plugin Check（PCP）の全項目パスと 2 要素認証が新規申請の必須要件**（2024-10-01 施行）。Security カテゴリは全パス必須、"Plugin repo" カテゴリも実質必須。
- レビュー待ちは **1〜10 営業日**（2026 年 8 月末時点でキュー 4,715 件、未処理の新規 167 件）。
- 提出は完成した zip。差し戻しは往復 1 回ごとに数営業日かかるため、**提出前に PCP を全パスさせることがリードタイム短縮の最大要因**。

## 3. アーキテクチャ

```
WordPress サイト
├── wp-admin（設定画面）
│   └── R2C 設定ページ ── REST ──> api.r2c.biz/v1/public/wp/*   [新規実装]
│                                   （プロビジョニング・設定同期）
│       ※ iframe は使用不可（ガイドライン #8）
│
└── フロント（wp_footer）
    └── <script src="https://api.r2c.biz/widget/{tenantId}.js" async>
                                  ↑ 既存の動的配信ルート
                                    src/api/widget/routes.ts
```

**プラグインは薄いラッパーに徹する。** ウィジェットの実装・プラン判定・ブランディングはすべてサービス側に置く。
これはガイドライン #5（トライアルウェア）・#10（クレジット表示）を同時に満たす唯一の構造でもある。

### 3.1 既存の 3 経路との関係

`CLAUDE.md` 絶対にやってはいけないこと #38 のとおり、ウィジェット配布は既に 3 経路ある。
プラグインは **① 動的版のみ**を使う。

| 経路 | 内容 | プラグインでの扱い |
|---|---|---|
| ① `GET /widget/:tenantSlug.js` | テナント設定を注入する動的版。`Cache-Control: max-age=300` | **これを使う** |
| ② `public/widget.js` + `data-tenant` | プラン判定を経由しない静的版（fail-open） | **使わない** |
| ③ `db === null` 時に ① が ② へリダイレクト | 設定が一切注入されない既知の穴 | 制御不能。DB 障害時の挙動として受容し、§7 の受け入れ条件に含めない |

**帰結:** プラグイン設定画面での変更は**最大 5 分反映が遅れる**。UI に明示すること（FR-09）。

## 4. 機能要件

### 4.1 接続・プロビジョニング

| ID | 要件 | 根拠 |
|---|---|---|
| **FR-01** | 未接続状態では**いかなる外部通信も行わない**。フロントにスクリプトを出力せず、管理画面からも R2C へ通信しない | GL#7 |
| **FR-02** | 接続画面に**同意チェックボックス**を置く。チェックなしでは接続ボタンを押せない。同意文には「送信されるデータの一覧」「R2C 利用規約 URL」「プライバシーポリシー URL」を明示する | GL#7 |
| **FR-03** | 接続時に送信するデータは以下に限定する: メールアドレス、サイト URL、サイト名、WordPress バージョン、プラグインバージョン、サイト言語（locale）。**投稿内容・ユーザー情報・アクセスログは送信しない** | GL#7 |
| **FR-04** | サーバ側は**サイト所有の証明を得てから**テナントとキーを発行する（§5.2）。証明前にキーを返してはならない | セキュリティ |
| **FR-05** | 既に R2C アカウントを持つ利用者のため、**API キーを手で貼り付ける経路も併設**する。サインアップ経路の失敗時のフォールバックにもなる | 実務 |
| **FR-06** | 設定画面は **WP 標準 UI（Settings API）で構成**する。`admin.r2c.biz` の iframe 埋め込みは行わない | GL#8 |
| **FR-07** | 「接続を解除」操作で、ローカルの資格情報を削除し、サーバ側のキーを失効させる。**R2C テナントとその会話データは削除しない**旨を UI に明示する | データ保全 |

| ID | 要件 |
|---|---|
| **FR-08** | 接続済みかつ「有効」設定時のみ、`wp_footer` で `wp_enqueue_script` により `https://api.r2c.biz/widget/{tenantId}.js` を `async` 付きで出力する |

## 5. サーバ側の新規実装（最大の開発項目）

**現状の制約:** テナント作成は `POST /v1/admin/tenants`（`src/api/admin/tenants/routes.ts:734`）で
`requireSuperAdmin` が掛かっている。**公開のセルフサインアップ経路は存在しない。**
D2（プラグイン内サインアップ）はこれを新設しない限り実現できない。

### 5.1 新設エンドポイント

| メソッド | パス | 用途 |
|---|---|---|
| `POST` | `/v1/public/wp/provision` | プロビジョニング開始。サイト検証チャレンジを返す |
| `GET` | `/v1/public/wp/provision/:token` | 検証・発行状態のポーリング。完了時に tenantId と widget キーを返す |
| `POST` | `/v1/public/wp/disconnect` | キー失効（テナントは残す） |

### 5.2 サイト所有証明（必須）

メールアドレスとサイト URL を自己申告させるだけでは、**第三者が他人のドメインで無制限にテナントを作れる**。
以下の二段で防ぐ。

1. **ドメイン所有証明** — プラグインが自サイトに REST ルート（例 `/wp-json/r2c/v1/verify`）を立て、
   プロビジョニング要求時に受け取ったワンタイムトークンを返す。R2C 側がその URL を取得し、
   トークン一致を確認する。これによりサイト URL の申告が実際の設置サイトであることが保証される。
2. **メール到達確認** — 確認メールのリンククリックまで、キーを発行しない。

**成功時にサーバが行うこと:**

- テナント作成（`plan = free_ad`）
- **`allowed_origins` にサイト URL を自動登録**（`src/lib/tenantConfigAudit.ts` が検出している
  「`allowed_origins` が実質空 → 全ドメイン許可の fail-open」を、この経路では構造的に起こさない）
- ウィジェット用途に**スコープを限定した API キー**を発行（管理 API を叩けないこと）

### 5.3 濫用対策

| 項目 | 要件 |
|---|---|
| レート制限 | IP 単位・ドメイン単位の双方。既存のレート制限機構に載せる |
| 重複登録 | 同一ドメインで既にテナントがある場合は新規作成せず、既存テナントへの接続要求として扱う（承認はメール経由） |
| 原価 | `free_ad` は原価を R2C が負担するプラン（`CLAUDE.md` #39）。**テナント単位の上限は実装済み**（`src/lib/billing/planQuota.ts`: `FREE_AD_MONTHLY_REQUEST_LIMIT = 1000` / `FREE_AD_MONTHLY_ADMIN_CONSULT_LIMIT = 30` / `FREE_AD_MONTHLY_CONVERSATION_LIMIT`）。**未実装なのはテナント数そのものの総量ガード**（§5.4）。`trackUsage` は請求ゼロでも必ず通す |

### 5.4 総量ガード（未実装 / 本要件で新設する）

**テナント 1 件あたりの上限は既に完備している。** 未実装なのは **テナント数そのものの上限**である。
現在の `free_ad` はすべて手動作成のため総量が自然に律速されているが、プラグイン公開はこの律速を外す。

| 項目 | 要件 |
|---|---|
| 総量上限 | プラグイン経由の `free_ad` 自動作成に **同時 100 テナント / 新規 30 件・日** の上限を置く（サーバ側保持、D7）。上限到達時は「順番待ち」として扱い、エラーで落とさない |
| アラート | `free_ad` 全体の当月原価が **¥20,000** を超えたら通知する（D7）。既存の原価集計（`src/lib/billing/tenantEconomics.ts`）に載せる |
| 監視 | 総量ガードは**プラグイン公開と同時に稼働している必要がある**。公開後に足す設計にしない |

> **注:** 本要件で最も見落としやすいのがこの 5.4 である。プラグイン公開は機能追加ではなく、
> **無料テナントの自動増殖経路の開通**であり、原価構造の変更にあたる。

## 6. 非機能要件

| ID | 要件 |
|---|---|
| **NFR-01** | 対応バージョン: **WordPress 6.0 以上 / PHP 7.4 以上**。`Requires at least` と `Requires PHP` は WP 5.8 以降**メイン PHP ファイルからパースされる**ため、readme だけでなくヘッダに書く |
| **NFR-02** | **Plugin Check（PCP）の全項目パス**を出荷条件とする。Security カテゴリは必須 |
| **NFR-03** | セキュリティ: 全フォームに nonce、全管理操作に `current_user_can('manage_options')`、入力は `sanitize_*`、出力は `esc_*`、全ファイル冒頭に `defined('ABSPATH') \|\| exit;`、全関数・クラス・option 名にプレフィックス |
| **NFR-04** | jQuery 等の WP 同梱ライブラリを再同梱しない（GL#13） |
| **NFR-05** | API キーは `wp_options` に `autoload = false` で保存し、管理画面では**マスク表示**する。**ローカルでの暗号化は行わない**（D6）。防御はサーバ側のスコープ限定キー・`allowed_origins` 束縛・接続解除時の即時失効で構成する |
| **NFR-06** | R2C API への通信は `wp_remote_post` / `wp_remote_get` を使い、タイムアウトを設定する。**API 到達不能時もサイトのフロントが壊れないこと**（スクリプトタグの出力は保存済み設定のみに依存し、リクエスト時に R2C へ問い合わせない） |
| **NFR-07** | 国際化: `load_plugin_textdomain` を実装。UI 文字列は英語で書き、日本語は翻訳ファイルで提供（主要市場は日本語） |
| **NFR-08** | フロントへの追加負荷: プラグインが出力するのは `<script async>` 1 本のみ。CSS・追加 JS をフロントに出さない |

## 7. 受け入れ条件

出荷（wordpress.org 提出）の可否は以下で判定する。

1. Plugin Check の全項目がパスする
2. **未接続状態でネットワークトレースを取り、R2C への通信が 0 件**である（GL#7 の実証）
3. 接続 → ウィジェット表示までを、テーマファイルを編集せずに完了できる
4. サイト所有証明を通さずに API キーが発行できない（他人のドメインを申告した場合に失敗する）
5. プラグイン同梱ファイルに難読化・minify されたコードが存在しない
6. プラグインのコードに、支払い状態で分岐する機能ロックが存在しない
7. readme.txt に External Services 節があり、送信データが FR-03 の一覧と一致する
8. 接続解除後、フロントにスクリプトが出力されない
9. R2C API 停止中でもサイトのフロントが正常に表示される（NFR-06）

## 10. 着手前ブロッカー

未決の設計判断は残っていない（D1〜D8 で確定済み）。以下は**実装ではなく先に潰すべき前提**であり、
どちらも WordPress プラグインとは独立に存在している欠陥である。

### B-1. 利用規約・プライバシーポリシーが未記入のまま本番公開されている（提出ブロッカー）

2026-09-04 実測:

| ファイル | 未記入箇所 |
|---|---|
| `public/legal/privacy.html` | 事業者の正式名称が `【要記入: 事業者の正式名称】` |
| `public/legal/terms.html` | 最終更新日・制定日・事業者名がいずれも `【要記入】` |

両ページは `https://r2c.biz/legal/` で公開済みかつ **LP のフッタと問い合わせフォームからリンクされている**。
D5 でこの URL を readme に載せる以上、**記入完了が提出の前提**になる。
取得情報の項目立て（対話内容・アカウント情報・利用状況/技術情報・登録コンテンツ）は FR-03 と整合しているため、
埋めるべきは事業者情報と日付のみ。

> これは WP プラグインの都合ではなく、**現に稼働中のサービスの法的文書の欠陥**である。プラグインの進行と無関係に修正すべき。

### B-2. 本リポジトリが PUBLIC かつライセンス未記載

`milechy/commerce-faq-tasks` は `visibility: PUBLIC` である一方、`LICENSE` ファイルが存在せず
`package.json` も `"private": true` でライセンス指定がない（＝法的には全権留保）。
D8 によりプラグインは別リポジトリに置くため**本要件の直接のブロッカーではない**が、
プラグインの readme から開発リポジトリを参照する導線が増えることで露出も増える。別途手当てすべき。
