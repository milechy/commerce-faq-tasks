## 0. 決定事項（着手前に確定済み）

| # | 決定 | 理由 |
|---|---|---|
| **D1** | **配布は wordpress.org 公式ディレクトリを優先**する。自社 zip 直配布は当面やらない | 発見性と信頼性。ただし後述の全ガイドライン適合が出荷条件になる |
| **D2** | **接続はプラグイン内サインアップ**（WP 管理画面からメール入力 → R2C テナント自動作成 → キー自動設定） | 導入摩擦の最小化。ただし**サーバ側に公開プロビジョニング API が存在しないため新規実装が必要**（§5） |
| **D3** | **v1.0 のスコープはウィジェット設置＋設定のみ**。WP 記事の知識源同期・WooCommerce 連携は v1.1 以降 | 最短で審査を通し、審査リスクを最小化する |
| **D4** | **slug は `r2c-ai-concierge`**、表示名は `R2C – AI Concierge & Chat for Customer Support`。タグは `chatbot` / `live chat` / `ai` / `customer support` / `faq` の 5 個 | 2026-09-04 実測で `r2c` / `r2c-chat` / `r2c-ai-concierge` / `rajiuce` / `ai-concierge` / `r2c-widget` はいずれも未使用。`r2c` 単体は 3 文字で検索に埋もれ他社の同名略称と衝突しやすく、`rajiuce` は英語圏で読めない。GL#17（他者商標を slug 先頭に置かない）・GL#12（タグ 5 個上限）を同時に満たす |
| **D5** | **利用規約 `https://r2c.biz/legal/terms.html` / プライバシーポリシー `https://r2c.biz/legal/privacy.html` を readme に記載する** | 両 URL とも到達可能（200）。ただし**中身が未記入のままであり、埋めるまで提出できない**（§10 BL-1） |
| **D6** | **API キーはローカルで暗号化しない。** `wp_options` に `autoload = false` で保存し、**キーのスコープ限定・ドメイン束縛・マスク表示・即時失効**の 4 点で守る | `AUTH_KEY` 由来の暗号化は鍵が同じ `wp-config.php` にあるため実効性がなく、監査でセキュリティシアターと見なされる。スコープ限定（chat のみ / 管理 API 不到達）と `allowed_origins` 束縛により、漏洩時の最悪ケースを「そのドメインでチャットが呼べる」に限定できる。両方とも既存機構で実現可能 |
| **D7** | **`free_ad` 総量ガードの初期値は「同時 100 テナント / 新規 30 件・日」、原価アラートは「`free_ad` 全体の当月原価 ¥20,000」** | 固定費が月 ¥25,655 に対し `free_ad` 枠を月 ¥30,000 と置く。上限張り付き時の 1 テナント最悪値は管理 AI ¥60〜90（`docs/ADMIN_AGENT_COST_REQUIREMENTS.md` の実数）＋会話 200 件分で月 ¥300〜500 と**見積もり**（会話単価は `costCalculator.ts` のモデル別のため推定値）。最悪値ベースで 60 件、実際は上限張り付きが稀なため初期値 100 件。アラートは枠の手前で鳴らす |
| **D8** | **プラグインは専用リポジトリ `milechy/r2c-wordpress-plugin` を新設し GPLv2 で公開**する。本リポジトリには置かない | wordpress.org が求めるのは開発リポジトリへのリンクのみでサーバコードの公開は不要（GL#4）。本リポジトリに GPLv2 のディレクトリを混ぜるとライセンス境界が曖昧になる。SVN 同期スクリプトの置き場としても独立が望ましい |
| **D9** | **設定の真実は常に R2C 側 DB に置く。WP 管理画面は遠隔操作であって権威ではない** | 位置・除外ページ・許可ドメインは **CopilotUI に既存のツールがある**（`set_widget_theme` / `update_excluded_page_patterns` / `update_allowed_origins`）。WP 側にも保持させると二重管理になり、禁止29（2つの列で二重管理したまま片方だけ直す）と同型の事故になる。R2C を正にすれば **CopilotUI 側の既存ツールに一切分岐を入れずに済む**（§13.2） |
| **D10** | **WordPress 内で完結させるのは「設置」まで。FAQ 登録・有人対応・課金・学習は CopilotUI へ誘導する** | R2C の価値の中心は CopilotUI 側にある（`add_faq` / `get_escalations` / `change_my_plan` / `get_knowledge_gaps` ほか）。WP 側に複製すると PHP で二重実装することになる。**ウィジェットは出たが FAQ がゼロ**という放置導線を作らないことが要件（§13.3） |
| **D12** | **メール到達確認をキー発行のブロッカーにしない。** サイト所有証明が通った時点でテナントとキーを発行し、メールは `inviteUserByEmail` による client_admin 招待として送る | 実装時に既存の招待経路（`src/api/admin/tenants/routes.ts` の `POST /v1/admin/tenants/:id/invite`）を読んで判断を変えた。これは「R2C App の client_admin アカウントを作り、パスワード設定画面へ誘導する」処理であり、**招待メールがそのまま D10（運用は R2C App へ誘導）の導線になる**。ブロッカーにすると、迷惑メール・企業のメールフィルタで止まった時点で導入が詰まり、§1 の「5 分以内に稼働」も達成できない。サイト所有証明という強い保証が既にあるため、メール確認の追加価値に対して摩擦が大きすぎる（§5.2） |
| **D11** | **Super Admin 側でプラグイン経由テナントを識別できるようにする**（`tenants` に流入元の列を追加し、一覧で識別、総量ガードの実績を監視画面に出す） | 現在 `tenants` に流入元を示す列が無く、**どれが WP 経由かを判別する手段がない**。WP-5 の総量ガードは、発火実績を目で確認できないと運用できない（禁止50: 監視対象が 0 件のときに「異常なし」と報告しない）（§13.5） |

## 1. 目的

R2C の AI 接客ウィジェットを、**WordPress サイト運営者が管理画面から数クリックで導入できる**ようにする。
現状の導入経路は「テナント登録 → 管理画面で API キー発行 → HTML に 1 行貼り付け」であり、
テーマファイル編集を伴うため WordPress 利用者層にとって障壁が高い。

**成功の定義（v1.0）:**

1. wordpress.org 公式ディレクトリに掲載されている
2. WP 管理画面のみで、テーマファイルを一切編集せずにウィジェットが稼働する
3. プラグイン有効化から稼働までの所要時間が **5 分以内**

### 2.1 審査プロセスの前提

- **Plugin Check（PCP）の全項目パスと 2 要素認証が新規申請の必須要件**（2024-10-01 施行）。Security カテゴリは全パス必須、"Plugin repo" カテゴリも実質必須。
- レビュー待ちは **1〜10 営業日**（2026 年 8 月末時点でキュー 4,715 件、未処理の新規 167 件）。
- 提出は完成した zip。差し戻しは往復 1 回ごとに数営業日かかるため、**提出前に PCP を全パスさせることがリードタイム短縮の最大要因**。

## 3. アーキテクチャ

```
WordPress サイト
├── wp-admin（設定画面）
│   └── R2C 設定ページ ── REST ──> api.r2c.biz/v1/public/wp/*   [新規実装]
│                                   （プロビジョニング・設定同期）
│       ※ iframe は使用不可（ガイドライン #8）
│
└── フロント（wp_footer）
    └── <script src="https://api.r2c.biz/widget/{tenantId}.js" async>
                                  ↑ 既存の動的配信ルート
                                    src/api/widget/routes.ts
```

**プラグインは薄いラッパーに徹する。** ウィジェットの実装・プラン判定・ブランディングはすべてサービス側に置く。
これはガイドライン #5（トライアルウェア）・#10（クレジット表示）を同時に満たす唯一の構造でもある。

### 3.1 既存の 3 経路との関係

`CLAUDE.md` 絶対にやってはいけないこと #38 のとおり、ウィジェット配布は既に 3 経路ある。
プラグインは **① 動的版のみ**を使う。

| 経路 | 内容 | プラグインでの扱い |
|---|---|---|
| ① `GET /widget/:tenantSlug.js` | テナント設定を注入する動的版。`Cache-Control: max-age=300` | **これを使う** |
| ② `public/widget.js` + `data-tenant` | プラン判定を経由しない静的版（fail-open） | **使わない** |
| ③ `db === null` 時に ① が ② へリダイレクト | 設定が一切注入されない既知の穴 | 制御不能。DB 障害時の挙動として受容し、§7 の受け入れ条件に含めない |

**帰結:** プラグイン設定画面での変更は**最大 5 分反映が遅れる**。UI に明示すること（FR-09）。

## 4. 機能要件

### 4.1 接続・プロビジョニング

| ID | 要件 | 根拠 |
|---|---|---|
| **FR-01** | 未接続状態では**いかなる外部通信も行わない**。フロントにスクリプトを出力せず、管理画面からも R2C へ通信しない | GL#7 |
| **FR-02** | 接続画面に**同意チェックボックス**を置く。チェックなしでは接続ボタンを押せない。同意文には「送信されるデータの一覧」「R2C 利用規約 URL」「プライバシーポリシー URL」を明示する | GL#7 |
| **FR-03** | 接続時に送信するデータは以下に限定する: メールアドレス、サイト URL、サイト名、WordPress バージョン、プラグインバージョン、サイト言語（locale）。**投稿内容・ユーザー情報・アクセスログは送信しない** | GL#7 |
| **FR-04** | サーバ側は**サイト所有の証明を得てから**テナントとキーを発行する（§5.2）。証明前にキーを返してはならない。**メール到達確認は発行の条件にしない**（D12） | セキュリティ |
| **FR-05** | 既に R2C アカウントを持つ利用者のため、**API キーを手で貼り付ける経路も併設**する。サインアップ経路の失敗時のフォールバックにもなる | 実務 |
| **FR-06** | 設定画面は **WP 標準 UI（Settings API）で構成**する。`admin.r2c.biz` の iframe 埋め込みは行わない | GL#8 |
| **FR-07** | 「接続を解除」操作で、ローカルの資格情報を削除し、サーバ側のキーを失効させる。**R2C テナントとその会話データは削除しない**旨を UI に明示する | データ保全 |

## 5. サーバ側の新規実装（最大の開発項目）

**現状の制約:** テナント作成は `POST /v1/admin/tenants`（`src/api/admin/tenants/routes.ts:734`）で
`requireSuperAdmin` が掛かっている。**公開のセルフサインアップ経路は存在しない。**
D2（プラグイン内サインアップ）はこれを新設しない限り実現できない。

### 5.1 新設エンドポイント

| メソッド | パス | 用途 |
|---|---|---|
| `POST` | `/v1/public/wp/provision` | プロビジョニング開始。サイト検証チャレンジを返す |
| `GET` | `/v1/public/wp/provision/:token` | 検証・発行状態のポーリング。完了時に tenantId と widget キーを返す |
| `POST` | `/v1/public/wp/disconnect` | キー失効（テナントは残す） |

### 5.2 サイト所有証明（必須）

メールアドレスとサイト URL を自己申告させるだけでは、**第三者が他人のドメインで無制限にテナントを作れる**。
以下の二段で防ぐ。

**ドメイン所有証明**（唯一の必須ゲート） — プラグインが自サイトに REST ルート
（`/wp-json/r2c/v1/verify`）を立て、プロビジョニング要求時に受け取ったワンタイムチャレンジを返す。
R2C 側がその URL を取得し、一致を確認する。これによりサイト URL の申告が実際の設置サイトであることが
保証される。取得は `src/lib/net/ssrfGuard.ts` の `safeFetch` 経由で行う（SSRF 対策を自前で書かない）。

> **v4.1 改訂（D12）:** v4.0 では「メール到達確認のリンククリックまでキーを発行しない」を二段目の
> 必須ゲートにしていたが、**外した**。サイト所有証明が通っている以上、そのサイトの管理者であることは
> 既に証明されている。メールをブロッカーにすると、迷惑メール・企業フィルタで止まった時点で導入が
> 詰まる。メールは **`inviteUserByEmail` による client_admin 招待**として送り、
> R2C App（CopilotUI）への導線として機能させる（D10 / D12）。
> 偽のメールアドレスを入れられた場合の被害は「招待が届かない」ことに限られ、他人のアドレスへの
> メール爆撃は §5.3 のレート制限で抑える。

**成功時にサーバが行うこと:**

- テナント作成（`plan = free_ad`）
- **`allowed_origins` にサイト URL を自動登録**（`src/lib/tenantConfigAudit.ts` が検出している
  「`allowed_origins` が実質空 → 全ドメイン許可の fail-open」を、この経路では構造的に起こさない）
- ウィジェット用途に**スコープを限定した API キー**を発行（管理 API を叩けないこと）

### 5.3 濫用対策

| 項目 | 要件 |
|---|---|
| レート制限 | IP 単位・ドメイン単位の双方。既存のレート制限機構に載せる |
| 重複登録 | 同一ドメインで既にテナントがある場合は新規作成せず、既存テナントへの接続要求として扱う（承認はメール経由） |
| 原価 | `free_ad` は原価を R2C が負担するプラン（`CLAUDE.md` #39）。**テナント単位の上限は実装済み**（`src/lib/billing/planQuota.ts`: `FREE_AD_MONTHLY_REQUEST_LIMIT = 1000` / `FREE_AD_MONTHLY_ADMIN_CONSULT_LIMIT = 30` / `FREE_AD_MONTHLY_CONVERSATION_LIMIT`）。**未実装なのはテナント数そのものの総量ガード**（§5.4）。`trackUsage` は請求ゼロでも必ず通す |

### 5.4 総量ガード（未実装 / 本要件で新設する）

**テナント 1 件あたりの上限は既に完備している。** 未実装なのは **テナント数そのものの上限**である。
現在の `free_ad` はすべて手動作成のため総量が自然に律速されているが、プラグイン公開はこの律速を外す。

| 項目 | 要件 |
|---|---|
| 総量上限 | プラグイン経由の `free_ad` 自動作成に **同時 100 テナント / 新規 30 件・日** の上限を置く（サーバ側保持、D7）。上限到達時は「順番待ち」として扱い、エラーで落とさない |
| アラート | `free_ad` 全体の当月原価が **¥20,000** を超えたら通知する（D7）。既存の原価集計（`src/lib/billing/tenantEconomics.ts`）に載せる |
| 監視 | 総量ガードは**プラグイン公開と同時に稼働している必要がある**。公開後に足す設計にしない |

> **注:** 本要件で最も見落としやすいのがこの 5.4 である。プラグイン公開は機能追加ではなく、
> **無料テナントの自動増殖経路の開通**であり、原価構造の変更にあたる。

## 11. 実装上の制約

### 11.1 既存コードへの統合方針 — 新規ファイルを安易に作らない

`CLAUDE.md` の明文規定をそのまま適用する:

> **新規ファイルを作ってよいのは**、テスト可能な純関数として切り出す場合のみ。
> その場合も `confirmPolicy.ts` / `agentAuditLog.ts` と同じ粒度・同じディレクトリに置き、隣に `*.test.ts` を作る。

本件でやることの置き場所は、**ほぼ全て既存にある**。以下は実コードで確認した対応表。

| やること | 置き場所（既存） | 作ってはいけないもの |
|---|---|---|
| 公開プロビジョニング API | `src/api/widget/` 配下。`registerWidgetRoutes(app, db)` と同じ `register*Routes(app, db)` の形にし、`src/index.ts` の既存の登録列に `if (db) register...` で並べる | 新しい express app・新しいサーバプロセス |
| **キーのドメイン束縛** | **`tenants.allowed_origins TEXT[]`**（テナント作成時に発行 origin を直接書く）。**★2026-09-04 実装時に訂正: 当初案の `tenant_api_keys.allowed_origins TEXT[]`（`phase_security_level3.sql`）はキー単位に列こそ存在するが、`originCheck.ts` を含めコード全体のどこからも SELECT されておらず enforcement に効いていなかった**。実際の enforcement は常にテナント単位（`tenants.allowed_origins`）だった | 第 2 のオリジン許可リスト |
| Origin 検証 | 既存 `src/api/middleware/originCheck.ts` | **`src/middleware/` にも別のミドルウェア群があるので取り違えない**（`inputSanitizer` / `promptFirewall` 等はそちら） |
| キーのスコープ限定 | **追加実装は不要**（実装時に判明）。`/v1/admin/*` は本番で `x-api-key` を一切受け付けない（`supabaseAuthMiddleware` の `x-api-key` 分岐は `ALLOW_INSECURE_DEV_AUTH` の dev バイパスのみ）ため、`tenant_api_keys` から発行した widget キーは構造的に管理 API へ到達できない。**列を追加する必要はなかった** | 第 2 のキーテーブル・不要な列追加 |
| **メール送信** | 既存 `supabaseAdmin.auth.admin.inviteUserByEmail`（`src/api/admin/tenants/routes.ts:1300` の招待経路）。**専用のメール基盤はこのリポジトリに存在しない** | nodemailer / SendGrid / Resend 等の新規導入 |
| テナント・運用者への通知 | `src/lib/notifications.ts` の `createNotification`（`recipientRole` / `recipientTenantId` を必ず添える） | 新しい通知テーブル |
| 原価の集計・アラート | 既存 `src/lib/billing/tenantEconomics.ts` | 新しい計測基盤（禁止32） |
| 定期処理 | `src/index.ts` の既存 `setInterval` 群（AlertEngine / pipelineQueue self-heal と同じ場所・同じ形） | cron / launchd / 新プロセス（禁止30 の多重起動も） |
| プラン判定 | 注入済み `db` に `queryTenantPlan` + `planHasFeature` | `tenantHasFeature`（内部で `getPool()` を呼びテストのモック Pool と食い違う） |
| ウィジェットの表示物 | `src/api/widget/widgetGenerator.ts` の設定注入 + `public/widget.js` の既存 Shadow DOM 構築部 | 第 2 の埋め込み経路・第 2 のウィジェット実装 |

> 「新しい名前空間を作る」以上のことをしない。認証層・レート制限・エラー形式は既存の作法に合わせる。

| 1 | `tenantId` を client 由来から取る | provision の応答を除き、`tenantId` を request body から受けない |
| 6 | 同じ関心事を 2 ファイルに複製したまま片方だけ直す | メール送信・Origin 検証・原価集計を書き起こさない（§11.1） |
| 8 | DB migration を自動実行する | スコープ列追加は人間承認。デプロイ手順に混ぜない |
| 10 | 費用が発生する操作を、計上しないまま開放する | `free_ad` でも `trackUsage` を必ず通す（請求ゼロでも `usage_logs` に残す） |
| 14 | 機能ゲートを UI 側だけに置く | プラグイン設定画面で隠すだけにせず、サーバ側で拒否する |
| 20 | 「存在しない」と「空」を同じ値で表現する | provision の状態は `pending` / `verified` / `expired` / `not_found` を区別する |
| 21 | HTTP ステータスの意味を潰して 1 つの文言にまとめる | 403（未検証）/ 404（トークン不明）/ 409（同一ドメインに既存テナント）/ 429（レート制限）を同じメッセージにしない |
| 22 | クライアントが送るヘッダを許可リストに足さずに増やす | プラグインが独自ヘッダを送るなら `src/lib/cors.ts` の `ALLOWED_HEADERS` に必ず追加する |
| 25 | セッション / キャッシュ / Map をテナント非スコープでキー付けする | provision トークンのインメモリ保持をするなら、そもそも DB に置く |
| 26 | 認証を fail-open にする | `WIDGET_JWT_SECRET` 未設定で素通ししない。ハードコードフォールバックを置かない |
| **27** | **公開配布物と管理 API で同じ署名鍵を使う** | プロビジョニングトークンは `SUPABASE_JWT_SECRET` で署名しない。`WIDGET_JWT_SECRET` 系で署名し `purpose` クレームで用途を固定する |
| **28** | **レートリミッタを認証前・全テナント単一バケットで運用する** | 認証前は nginx 注入の `X-Real-IP` をキーにした IP リミッタ、認証後は `tenantId` キー。`trust proxy` 未設定のため `req.ip` は常に `127.0.0.1` で使い物にならない |
| **38** | ウィジェットの配布経路が 2 系統あり、キャッシュされる事実を無視する | プラグインは①動的版のみを使う。②静的版（`data-tenant`）へ流れる実装にしない。反映は最大 5 分遅れる |
| **39** | 原価の負担者が反転する機能を、上限なしで開放する | §5.4 の総量ガードが公開と同時に稼働していること |
| 41 | 環境変数だけで有効／無効が決まる機能を新設する | プロビジョニング経路の可否を env トグルだけに委ねない |
| 44 | 押せるのに何も起きない UI を置く | 未接続時に設定項目を押せる状態で並べない |
| 50 | 監視の対象が 0 件のときに「異常なし」と報告する | `free_ad` が 0 件のとき原価アラートを「正常」と報告しない |

### 11.4 プラグイン側（PHP）の制約

- 全ファイル冒頭に `defined('ABSPATH') || exit;`
- 全フォームに nonce、全管理操作に `current_user_can('manage_options')`
- 入力は `sanitize_*`、出力は `esc_*`
- jQuery 等の WP 同梱ライブラリを再同梱しない（GL#13）
- `wp_remote_post` / `wp_remote_get` に**必ずタイムアウトを設定**する
- フロントへの出力は `<script async>` 1 本のみ。CSS・追加 JS を出さない
- `uninstall.php` でプラグインが作成した option を全削除する

## 12. テスト観点

### 12.1 正常系

| # | 観点 |
|---|---|
| N-1 | 未接続 → 同意チェック → 接続 → 確認メール → ウィジェット表示、の通し |
| N-2 | API キー手動貼り付けだけでの接続（サインアップ経路を使わない） |
| N-3 | 表示位置の 4 隅 × オフセットの反映 |
| N-4 | 除外ページ指定（投稿タイプ別・特定固定ページ）でスクリプトが出ない |
| N-5 | 接続解除でローカル資格情報が消え、サーバ側キーが失効する |
| N-6 | 接続状態の表示（テナント ID・プラン・稼働可否）が実態と一致する |
| N-7 | プロビジョニング成功時に `allowed_origins` にサイト URL が自動登録される |
| N-8 | `free_ad` として作成され、`trackUsage` が請求ゼロでも通る |

### 12.2 異常系・境界値

| # | 観点 | 期待 |
|---|---|---|
| X-1 | サイト所有証明の REST ルートが応答しない | キーを発行しない。解決方法を伴うエラー |
| X-2 | 確認メールのトークン期限切れ | `expired` を返す。`not_found` と区別する（禁止20） |
| X-3 | 同一ドメインに既にテナントがある | 新規作成せず 409。既存テナントへの接続要求として扱う |
| X-4 | レート制限到達 | 429。**他テナントのウィジェットが巻き添えで 429 にならないこと**（禁止28） |
| X-5 | 総量ガード到達 | 「順番待ち」として正常系の分岐で返す。エラーで落とさない |
| X-6 | オフセット値 `-1` / `0` / `320` / `321` / `99999` / 文字列 | 0〜320 に丸める。既存 `public/widget.js` の値域と一致させる |
| X-7 | 除外パターンに正規表現メタ文字・極端に長い文字列・大量件数 | サーバ側で拒否または安全に丸める |
| X-8 | メールアドレスの形式不正・国際化ドメイン | Zod で 400 + `details` |
| X-9 | サイト URL が `http://` / 末尾スラッシュ有無 / www 有無 / ポート付き | 正規化して `allowed_origins` に入れる。**ワイルドカード・非 https・スキーム無しがすり抜ける既知の穴**（Asana 1218088720698659）を再現しないこと |
| X-10 | R2C API が 500 / タイムアウト / DNS 解決不能 | フロントは無傷。管理画面は解決方法を伴うエラー |
| X-11 | DB が `null`（`db === null`） | 動的ルートは静的版へリダイレクトする既知の経路（禁止38 の③）。プロビジョニングは 503 で明確に断る |
| X-12 | `WIDGET_JWT_SECRET` 未設定 | fail-closed。起動時に落ちる（禁止26） |

### 12.3 ユーザーがやりそうなイレギュラーな操作

**ここが本要件で最も事故が出る領域。** WordPress 利用者は「サイトを複製する」「プラグインを消して入れ直す」を日常的にやる。

| # | 操作 | 起きること / 求める挙動 |
|---|---|---|
| **I-1** | サイトのドメインを変更する（独自ドメイン移行、`http`→`https`、www の有無変更） | `allowed_origins` が古いままで**ウィジェットが無言で止まる**。管理画面で不一致を検出し、解決方法を提示する。ここを黙って失敗させない |
| **I-2** | 本番サイトを丸ごと複製してステージング環境を作る | 同じキーが 2 ドメインで動く。`allowed_origins` で弾かれるが、**「なぜ動かないか」が分かる文言**を出す |
| **I-3** | プラグインを削除して再インストールする | `uninstall.php` で option が消えた後、同じドメインで再接続 → **2 つ目のテナントを作ってはいけない**。E-3 の 409 経路に合流させる |
| **I-4** | 同じサイトから別のメールアドレスでもう一度サインアップする | 同上。ドメイン単位で既存テナントへ寄せる |
| **I-5** | R2C 管理画面（admin.r2c.biz）側でキーを削除してから、WP の設定を触る | WP 側は「接続済み」と表示したまま動かない状態になる。**接続状態を実サーバに問い合わせて表示する**か、失効を検知して未接続へ落とす |
| **I-6** | 確認メールのリンクを 2 回クリックする | 2 回目も成功として扱う（冪等）。キーを 2 本発行しない |
| **I-7** | 確認メールを何日も放置してからクリックする | `expired` を明示し、再送導線を出す（X-2） |
| **I-8** | Basic 認証・IP 制限・メンテナンスモードの下にあるサイトで接続する | サイト所有証明が到達できず失敗する。**「なぜ到達できないか」を具体的に出す**。到達不能を「メールが届かない」と誤診させない |
| **I-9** | `localhost` / `*.local` / 内部 IP のローカル開発環境で接続する | R2C から到達不能。事前に判定して「公開サイトが必要」と伝える。試行してタイムアウトさせない |
| **I-10** | プラグインを有効化したまま、テーマに旧来の手貼り `<script>` も残す | **ウィジェットが二重表示される**。プラグイン側で既存の埋め込みを検出して警告するか、少なくとも readme と設定画面に明記する |
| **I-11** | プランをアップグレードした直後に WP 画面を見る | 動的版は `max-age=300` のため**最大 5 分反映が遅れる**（禁止38）。「すぐ反映される」と読める文言を書かない |
| **I-12** | `free_ad` の月次上限（会話 200 件）に達した状態でサイトを見る | ウィジェットが止まる。テナント側の管理画面で理由が分かること。**エンドユーザーにエラーを見せない** |
| **I-13** | WordPress マルチサイトで有効化する | v1.0 はスコープ外。**動くふりをせず**、明示的に非対応と伝える |
| **I-14** | 接続解除した直後に再接続する | キー失効とテナント存続の組み合わせで矛盾しないこと。会話データが消えていないこと（FR-07） |
| **I-15** | WP の表示言語を英語以外に切り替える | UI が英語のままでも壊れない。翻訳未提供の言語でフォールバックする（NFR-07） |
| **I-16** | PHP 7.3 / WordPress 5.9 など要件未満の環境で有効化する | 有効化時に明確に拒否する。半分動く状態にしない |
| **I-17** | R2C API が停止している最中にプラグインを有効化・設定する | フロントは無傷（X-10 / NFR-06）。管理画面は「今は接続できない」と伝え、設定入力自体は失われない |
| **I-18** | 複数の WP 管理者が同時に設定画面を編集する | 後勝ちで黙って上書きしない。既存の楽観ロック（Asana 1217889968865474）の方針に揃える |

## 13. UI・UX 要件（面は 3 つある）

**v3.0 までこの章は存在せず、R2C 側の面が完全に抜けていた。** 本件で触る面は WordPress 管理画面だけではない。

| 面 | 誰が使うか | 本件での役割 |
|---|---|---|
| **WordPress 管理画面**（プラグイン） | テナント | **設置と遠隔操作のみ。** 運用機能は持たない |
| **CopilotUI**（`/copilot-preview`） | テナント | **運用の唯一の場所。** FAQ・有人対応・課金・学習はすべてここ |
| **Super Admin**（`/admin/tenants`） | R2C 運営 | 流入元の識別と総量ガードの監視 |

> **テナント向けの「UI/UX」は CopilotUI を指す。** 旧 admin-ui（`/admin/*`）だけに実装しても要件を満たさない。
> 逆に **CopilotUI に super_admin 限定機能を足してはならない**（PR #507 で誤実装 11 ツールを撤去した先例あり）。

### 13.1 責務分担

| 項目 | WP 管理画面 | CopilotUI | Super Admin |
|---|---|---|---|
| 接続・接続解除 | **○（ここだけ）** | 状態の表示のみ | 状態の表示 |
| 表示位置・オフセット | 遠隔操作 | **○（真実）** | — |
| 除外ページ | 遠隔操作 | **○（真実）** | — |
| 許可ドメイン | 接続時に自動登録 | **○（真実）** | ○ |
| 埋め込みコードの案内 | 不要（プラグインが出力） | **表示を変える**（§13.4） | ○ |
| FAQ 登録・編集 | **×**（導線のみ） | ○ | ○ |
| 有人対応・エスカレーション | **×** | ○ | ○ |
| 課金・プラン変更 | **×**（導線のみ） | ○ | ○ |
| 流入元の識別・総量監視 | — | — | **○（ここだけ）** |

### 13.2 設定の真実は R2C 側にある（D9）

| ID | 要件 |
|---|---|
| **FR-21** | 位置・除外ページ・許可ドメインの**唯一の真実は R2C 側 DB**。WP は `wp_options` にキャッシュとして持つが権威ではない |
| **FR-22** | WP 画面での変更は**即座に R2C へ PATCH し、成功して初めてローカルに反映**する。ローカル保存→後で同期、にしない |
| **FR-23** | WP 設定画面を開いたとき、**R2C から現在値を取得して表示**する。CopilotUI 側で変更された値が WP 画面に出ないこと（stale 表示）を許さない |
| **FR-24** | **R2C API 到達不能時は設定変更を受け付けない。** 「保存できたように見せて実際は保存されていない」を作らない（→ 禁止44: 押せるのに何も起きない UI） |
| **FR-25** | **CopilotUI 側の既存ツールに WP 分岐を入れない。** `set_widget_theme` / `update_excluded_page_patterns` / `update_allowed_origins` は現状のまま動く。これが D9 を選んだ最大の実利であり、**分岐を足したくなったら設計が間違っている** |

### 13.3 WordPress のみのテナントの導線（D10）

R2C の価値の中心は CopilotUI 側にあり、プラグインが担えるのは設置だけである。
**接続が完了した瞬間が最も放置されやすい**（ウィジェットは出るが FAQ がゼロ）。

| ID | 要件 |
|---|---|
| **FR-26** | 接続完了後、WP 設定画面に「**次にやること**」を出す。最低限「FAQ を登録する」「会話を見る」の 2 つと、R2C App への導線 |
| **FR-27** | **FAQ が未登録のまま稼働している場合、WP 設定画面で警告する。** ただし通知は**プラグイン設定画面内に限定**し、サイト全体の admin notice にしない（GL#11） |
| **FR-28** | WP 画面から FAQ 登録・有人対応・課金の機能を**提供しない**。導線（リンク）のみ。PHP で CopilotUI を再実装しない |

### 13.4 CopilotUI に必要な変更

| ID | 要件 |
|---|---|
| **FR-29** | **`get_embed_code` が WP 経由テナントに手貼りコードを勧めない。** 「WordPress プラグインで設置済み」と返す。現状のまま手貼りを案内すると、プラグインと二重に貼られてウィジェットが 2 つ出る（→ §12.3 I-10） |
| **FR-30** | 接続状態（プラグイン版・サイト URL・最終確認時刻）を CopilotUI から確認できる。**設定変更は既存ツールのまま**（FR-25） |

### 13.5 Super Admin に必要な変更（D11）

| ID | 要件 |
|---|---|
| **FR-31** | `tenants` に**流入元の列**を追加する（`manual` / `wordpress_plugin`）。migration は `ADD COLUMN IF NOT EXISTS` + `COMMENT ON COLUMN`、既定値は既存行を壊さない値にする |
| **FR-32** | テナント一覧で**流入元を識別できる**ようにする |
| **FR-33** | 監視画面に**総量ガードの実績**を出す（`free_ad` 同時稼働数 / 当日の新規作成数 / `free_ad` 全体の当月原価）。**0 件のときに「異常なし」と表示しない**（→ 禁止50。0 件は「まだ流入が無い」であって「正常」ではない） |

### 13.6 UI 固有のやってはいけないこと

- **CopilotUI に super_admin 限定機能を足す。** テナント専用面である（PR #507 の先例）。
- **旧 admin-ui（`/admin/*`）だけに実装する。** テナント向けの面は CopilotUI であり、旧 UI のみの実装は未完了とみなす。
- **WP 画面に R2C の運用機能を複製する。** D10 に反し、PHP 側に第 2 の実装を抱えることになる。
- **設定を WP 側に保持して「あとで同期」する。** D9 に反する。同期は必ず失敗し、どちらが正か分からなくなる。
