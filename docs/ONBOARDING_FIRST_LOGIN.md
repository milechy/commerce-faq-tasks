## 1. 本質的に解決すべき課題

**現行オンボーディングは「価値が出る一歩手前」で終わる設計になっている。**

R2C の価値はエンドユーザー（テナントのお客様）との会話が発生して初めて生まれる。しかし現行フローのゴールは *FAQ たたき台を N 件登録すること* である。ウィジェットが自社サイトに設置されていなければ、FAQ を何件入れても会話は 0 件のままで、テナントから見れば「何も起きていない」。

課題は3層ある。

1. **ゴール定義の誤り** — 「業種に答えた」を完了とみなしており、稼働（アクティベーション）を計測できていない（§0.2）。
2. **初回体験の入口が分裂している** — 同じオンボーディングが2実装で並存し、完了条件すら違う。`docs/CHAT_SURFACE_DECISION.md` §3.1 が記録した事故（正しい実装が同リポジトリにあるのに再利用されず、日本語入力が約13日壊れた）と同型の構造が、オンボーディングでも起きている。
3. **フローの進行が LLM の裁量に載っている** — 業種チップは `__real:業種は「X」です。この業種のFAQテンプレートを提案してください。` という自然文を送るだけで（`index.tsx:167-170`）、ツールが呼ばれる保証がない。確認チップの出現判定は `a.result.includes("よろしければ登録しますか")` という文字列一致（`:527`）。文言変更やモデル差し替えで**例外を出さずに**壊れる。

## 2. ユーザーが本当に得たい価値

テナント管理者（店舗オーナー・EC担当）が初回ログインで欲しいのは「AI接客を**設定すること**」ではなく、**「自分の代わりに問い合わせに答えてくれる状態」**である。初回に抱える不安は3つ。

- **これは自分の店のことを分かってくれるのか** — 汎用回答ではなく、自分の言葉・自分の営業時間で答えてくれるか
- **あと何をすれば動くのか** — 残り作業と現在地が見えるか
- **お客様に間違ったことを言わないか** — 公開前に確かめる手段があるか

チャットUIの本質的な優位は **「設定項目を覚えなくてよい」** ことである。したがって初回体験の理想形は「フォームのチャット置き換え」ではなく、**最初の一往復で自分の店の答えが返ってくること** — 「営業時間を聞かれたらこう答えます」を体験させ、その場で直させる。これが GUI ウィザードでは作れない差分であり、チャットで作る理由そのものである。

## 3. 決定事項（2026-07-31, hkobayashi）

| # | 論点 | 決定 |
|---|---|---|
| A | 初回ログインの着地面 | **新規テナントのみ新UI（`/copilot-preview`）を既定に**。既存テナントの動線は変えない |
| B | オンボーディングのゴール | **初回の実会話が発生するまで** |
| C | テンプレFAQ | **下書き（非公開）で投入し、確認後に公開** |
| D | 代行導線 | **必要**（伴走・代行が主経路） |

### 3.1 この4決定から演繹される構造

**① オンボーディングは初回セッション内で閉じない（B）**

ゴールを「実会話1件」に置いた時点で、達成はテナントの操作の外側で起きる（サイトにタグを設置 → 後日エンドユーザーが訪れる）。したがって:

- **中断・再開が必須要件に昇格する。** 現状は会話が復元されるとブートストラップ自体をスキップするため（`index.tsx:580-587`）、2回目のログインで「次に何をすべきか」が消える。ここが最大の実装欠落。
- **「設置したが会話がまだ来ていない」状態を表現する必要がある。** `chat_sessions`（`src/api/admin/chat-history/migration.sql:3-12`）の有無で「実会話が起きたか」は判定できるが、**ウィジェットが設置されたかを検知するシグナルは存在しない**。この2状態を区別できないと、詰まっているテナントを救えない。

**② 「公開」がアクティベーション経路上の必須ゲートになる（B × C）**

C（下書き投入）と B（実会話ゴール）は素直に組むと矛盾する。**知識が非公開のまま会話が来ると、AIが何も答えられない**。したがって:

> 初回セッションのゴールは「テンプレを N 件入れた」ではなく、**「テナントが内容を確認して、1件以上を公開した」** に置く。

これは §2 の「最初の一往復で自分の店の本物の答えが返ってくる」と一致する。ここが初回セッションの唯一の必達点であり、それ以外（アバター、CVタグ、GA4）は初回では必須にしない。

**③ 着地判定と完了判定を混ぜてはいけない（A × B）**

`onboarding_completed_at` を着地面の分岐に使うと、B で定義し直す完了条件（＝実会話発生）と結合する。**「実会話が来るまで新UIに着地し続ける」は誤った挙動**である。状態を分離する。

| 状態 | 意味 | 用途 |
|---|---|---|
| 着地面の判定軸 | このテナントは新UI世代か | A の分岐。一度決まったら実質不変 |
| 業種回答済み | 業種ヒアリングを通過 | 挨拶の再表示抑止 |
| 知識公開済み | 確認済みの知識が1件以上公開されている | 初回セッションの必達点 |
| 設置検知 | ウィジェットのロードを観測した | 「次の一手」の出し分け |
| 初回実会話 | `chat_sessions` に実会話が1件以上 | **アクティベーション＝真の成功指標** |

**決定（実装着手前に確定）:**

- **決定1（知識公開済みの導出範囲）:** テナント**全体**の `faq_docs` に `is_published = true` が1件以上あるかで判定する。オンボーディング由来の知識に限定しない。理由: この段階の意味は「AIが答えられる状態か」であり、知識の出自は問わない。オンボ以外の経路（旧来のFAQ手動登録等）で既に公開済みのテナントを、この段階が未達扱いにする方が誤りである。
- **決定2（設置検知の判定手段）:** `/api/widget/features` への到達で判定する（詳細と実測は P4 = §4.1-5）。実測の結果、到達性に問題があれば `/api/events` にフォールバックする。
- **決定3（同一テナント2人目の管理者、旧 X-8）:** 完了フラグは**テナント単位のまま**とする。2人目の管理者向けの専用案内はスコープ外。理由: ユーザー単位の状態を持つと `tenants` 1テーブルで完結する状態モデル（本章冒頭の設計）を壊し、複数管理者が同時に別々のオンボーディング状態を持つ複雑さに見合う価値がない。2人目が入った時点で大半のテナントは既に業種回答・知識公開を終えているため実害は小さい。

加えて実装上の制約がある。現在の着地判定は `isChatFirstDefaultEnabled()` という**同期の localStorage 読み取り**（`App.tsx:119-122`、`chatFirstDefault.ts:9-15`）だが、「新規テナントか」は**サーバの状態**である。認証直後にこれを取得するまで着地先が決まらないため、**旧UIを一瞬描画してから新UIへ飛ぶ（ちらつき・二重着地）**が起きる。判定情報をどこで持つかが設計上の必須論点。

**④ 代行を主経路にすると actor の記録が要る（D）**

`!previewMode && user?.role === "client_admin"` の除外（`index.tsx:591`）を解除するだけでは足りない。代行でセットアップした分がテナント自身の到達として集計されると、**アクティベーション率が実態より良く見える**（伴走が効いているのか、プロダクトが自走できているのかを区別できなくなる）。各段階の到達に actor（テナント本人 / super_admin代行 / Sai代行）を記録し、指標を分けて集計する。

## 5. 成功の定義

**主指標：初回ログインから7日以内に、エンドユーザーとの実会話が1件以上発生したテナント比率（アクティベーション率）。テナント本人到達／代行到達を分けて集計する。**

FAQ 登録件数を主指標にしてはならない。それは現行設計が既に最大化していて、かつ価値と相関しない数字である。

| 補助指標 | 合格ライン |
|---|---|
| 初回セッション内に確認済み知識を1件以上**公開**した率 | 上げる（現状値をまず測る） |
| 埋め込みコード提示 → 設置検知 の到達率 | 上げる |
| テンプレ既定値のまま公開された件数 | **0件** |
| オンボーディングの誤再表示率 | **0%**（§0.2 の現行バグ） |
| 2回目以降のログインで「次の一手」が提示された率 | 100% |

**前提条件（2026-07-31 実測により更新）:** Asana `1216970103691946`「実ユーザーとテスト/ボットトラフィックの分離」は Asana 上は未完了だが、**実装は既に着地済み**である。`src/lib/traffic/trafficSource.ts:23` の `TrafficSource`（`"user" | "e2e" | "chat_test" | "demo" | "unknown"`）が `chat_sessions.metadata.source` に記録される（`src/api/admin/chat-history/chatHistoryRepository.ts:45-57`、セッション新規作成時のみ確定・以降は保持）。したがって主指標の算出は `metadata->>'source' = 'user'` で絞るだけでよく、**新規実装は不要**。Asana 側のクローズは本ドキュメントの範囲外。

### 5.1 ベースラインSQL（改修前の現状値。読み取りのみ）

既存の `src/api/admin/analytics/summaryQueries.ts:319-330`（`t.created_at` を「テナントの起算点」の代理指標として使う既存パターン）に倣う。**専用の「初回ログイン」イベントは記録されていない**ため、`tenants.created_at` を初回ログイン日時の代理として使う（既存踏襲の制約であり本タスクの新規欠陥ではない）。

```sql
-- 主指標: 作成(≒初回ログイン)から7日以内に実会話(source='user')が発生したテナントの比率
WITH first_real_session AS (
  SELECT tenant_id, MIN(started_at) AS first_at
  FROM chat_sessions
  WHERE metadata->>'source' = 'user'
  GROUP BY tenant_id
)
SELECT
  COUNT(*) FILTER (
    WHERE frs.first_at IS NOT NULL
      AND frs.first_at <= t.created_at + INTERVAL '7 days'
  ) AS activated,
  COUNT(*) AS total,
  ROUND(
    COUNT(*) FILTER (WHERE frs.first_at IS NOT NULL AND frs.first_at <= t.created_at + INTERVAL '7 days')::numeric
    / NULLIF(COUNT(*), 0) * 100,
    1
  ) AS activation_rate_pct
FROM tenants t
LEFT JOIN first_real_session frs ON frs.tenant_id = t.id
WHERE t.created_at <= NOW() - INTERVAL '7 days';  -- 判定期間(7日)が満了したテナントのみを母集団にする
```

このクエリは読み取りのみで、コード変更を伴わない。**本番DBへの接続は人間の承認事項**（`CLAUDE.md` VPSデプロイルール）のため、実行はここでは行わない。P1 の完了条件は「このクエリが `docs/ONBOARDING_FIRST_LOGIN.md` に記載されていること」までとし、実行と数値の記録（`activated` / `total` / `activation_rate_pct`）は本番DB接続権限を持つ人間が行う。この数値が「改修前のベースライン」であり、P6（新UI着地）投入後に同じクエリを再実行して比較する。

## 6. 実装上の制約

### 6.1 既存コードへの統合方針（新規ファイルを安易に作らない）

この機能で必要になる要素は、ほぼすべて既存の置き場所が決まっている。新規作成は原則不要。

| 実現したいこと | 置く場所（既存） | 補足 |
|---|---|---|
| チャット送信・sessionId・履歴・`targetTenantId`・エラー文言 | `admin-ui/src/lib/useAgentChatTransport.ts` | 抽出済み（`:92-158`）。`surface` 対応済み（`:22, :124`）。**新しい `fetch` を書かない** |

### 6.2 守るべき設計原則・命名規則・既存パターン

**`CLAUDE.md` Core Principles（本件で特に効くもの）**

- **Security First** — `tenantId` は JWT / APIキーからのみ取得し、**body から取らない**。代行時も「`targetTenantId` は super_admin のときのみ有効」という既存条件（`agentRoutes.ts:651`）を変えない
- **Mobile First** — タップ領域 ≥44px、フォント ≥16px、**390px 幅で先に確認**。初回体験はモバイル比率が最も高い
- **Partner Friendly** — 専門用語を使わない。すべてのエラーに親切な文面、すべての操作に成功フィードバック

**Definition of Done（Gate）**

`pnpm typecheck` 0 errors → `pnpm lint` 0 warnings → `pnpm test` 全パス → `pnpm test:e2e` モバイルビューポート通過 → Gate 2.5 Codex review で P0/P1 なし。ブランチは `feature/<asana-id>-<short-description>`、**main 直コミット禁止（test-only も例外なし）**。

**既存パターンに合わせる**

| 対象 | 規約 |
|---|---|
| ツール名 | snake_case の `動詞_目的語`。既存の語彙（`get_*` `set_*` `save_*` `suggest_*` `import_*` `commit_*` `discard_*`）に合わせる |
| ツール戻り値 | 日本語・500字以内に `truncate`（`actionExecutor.ts:203`） |
| 副作用の失敗耐性 | 監査（`agentRoutes.ts:102-122`）・計測・embedding 生成はすべて **fire-and-forget**。「記録の失敗がチャット応答を壊してはならない」。オンボ段階の記録も同じ扱いにする |
| localStorage キー | `r2c_` プレフィックス（`r2c_chat_first_default`、`chatSessionKey()`） |
| migration | 機能ディレクトリ内に `migration_<機能>.sql`、`ADD COLUMN IF NOT EXISTS` + `COMMENT ON COLUMN` で意味を明記（`migration_onboarding.sql` が手本） |
| テスト配置 | バックエンド: jest、ソース隣に `*.test.ts`（横断は `tests/api/`）／admin-ui: vitest + happy-dom + testing-library、ソース隣に `*.test.tsx`／E2E: playwright `tests/e2e/*.spec.ts` |

**「文字列マーカー」規約についての注意**

このリポジトリは既に3箇所で応答文の部分一致に依存している。

| 箇所 | マーカー |
|---|---|
| 確認ブロック判定（フロント） | `確認が必要` / `確認をスキップできません`（`index.tsx:507-527`） |
| 監査の成功判定 | `successMarker: 'を更新しました'` 等（`agentRoutes.ts:89-100`） |
| 計測のブロック判定 | `確認が必要です`（`docs/AGENT_METRICS.md`。フロントと1文字違う点に注意が明記されている） |

`docs/AGENT_METRICS.md` はこれを明示的に「規約」と呼んでいる。したがって **既存3箇所と別方式を混在させない**（変えるなら3箇所同時。それは本件のスコープ外＝§4.2）。同時に、**新しいオンボーディング段階の判定をこの方式に新たに乗せない**（§6.3-1）。既存規約は既存の範囲で維持し、新規は構造化データで判定する、という線引きである。

### 6.3 やってはいけないこと

1. **オンボーディングの進行判定を LLM の応答文の文字列一致に依存させない。** `index.tsx:527` の方式を新しい段階に横展開しない。段階はツールの構造化結果または `/my-tenant` の状態で判定する
2. **`onboarding_completed_at` の意味を上書きしない。** 既存2実装（`routes.ts:223-226` / `actionExecutor.ts:474-479`）が別条件で書いている列。意味を変えると既存テナントの判定が過去に遡って変わる。**列を足して既存は温存する**
3. **着地面の分岐に「初回実会話」を使わない。** 実会話が来るまで新UIに固定され続ける
4. **テンプレFAQを `is_published = true` で登録しない**（決定C）。`actionExecutor.ts:457-461` と旧UI経由の `/v1/admin/knowledge/text/commit`（`OnboardingModal.tsx:62-68`）の**両方**を直す
5. **4本目のチャット実装 / IMEハンドラ / 3本目のオンボーディングUIを作らない。** チャット実装は既に3本（`AdminAgentPanel` / `copilot-preview` / `chat-test`）、オンボーディングは2本ある
6. **オンボーディング進行を localStorage に持たない。** ブラウザを変えると消え、代行（決定D）とも整合しない。サーバが正
7. **`actionExecutor.ts` に計測コードを足さない**（`docs/AGENT_METRICS.md` の明示制約）
8. **super_admin 専用機能を `/copilot-preview` に足さない**（PR #507 で誤追加の11ツールを撤去した経緯）。決定Dの代行は「super_admin がテナントの画面を**テナントとして**操作する」形であって、専用機能の追加ではない。この線を越えない
9. **確認ゲートを迂回するツールを新設しない。** `confirmPolicy` の分類対象から漏れる書き込み経路を作らない
10. **DB migration を自動実行しない**（`CLAUDE.md`: 不可逆操作は人間承認。24h自走中は禁止項目）
11. **オンボーディング中に同タブで旧UIへ遷移させない。** 既存は別タブ固定で会話を守っている（`index.tsx` の旧UI案内カード）。同タブにすると会話と進行が飛ぶ
12. **業種テンプレのコピーを3つ目に増やさない。** 既存2ファイルの重複解消は歓迎だが、増やすのは禁止
